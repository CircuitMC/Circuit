# Performance

This note records how the engine spends a tick and what was changed after the differential tests passed. Every change keeps the rules' semantics: `simulation_tests` compares the runtime with the sequential oracle at 1, 2, 4, 8 and 16 workers, under seeded schedules and injected aborts, and the target-version traces still pass.

## Method

```bash
xmake f -m release -y && xmake build circuit-server
xmake run circuit-server --profile-fixture "$PWD/tests/fixtures/workloads/observer_clocks.ctrace" --ticks 600 --workers 4
```

The profiler runs a workload's setup, then times 600 ticks. It reports:
- **Tick times:** mean, p50, p95, p99 and maximum.
- **Phase times.**
- **Work and coordination:**
  - *Rule work:* time tasks spend in rule code.
  - *Critical path:* for each runner call, the longest task, summed. This is the serial part a perfect scheduler could not avoid.
  - *Runner and coordination:* time inside the job runner, and coordination outside it, including the commit.

Times come from a release build (GCC 13) on an Intel Core Ultra 7 270K Plus with 24 threads under WSL 2. The five workloads are generated by `tools/generate_workloads.py`.

Before the changes, more workers made most workloads slower. After them, the worker count no longer costs time, and every workload is faster.

## Where the time goes

At 4 workers, after the changes:

| Workload | Rule work | Critical path | Coordination outside the runner (commit) |
| --- | --- | --- | --- |
| dust_clocks | 1,351 ms | 1,351 ms | 23 ms (9 ms) |
| observer_clocks | 154 ms | 154 ms | 42 ms (10 ms) |
| piston_engines | 164 ms | 164 ms | 44 ms (17 ms) |
| hopper_lines | 62 ms | 33 ms | 32 ms (10 ms) |
| water_flood | 8 ms | 5 ms | 4 ms (1 ms) |

**The critical path is the limit.** In the clock and piston workloads the critical path equals the rule work. The machines interact across chunk borders, so the adaptive layout merges their columns into one region, and that region's task does all the work. More workers cannot shorten this: the parallel design gains only where activity falls into independent regions. In the dust workload a long redstone line updates in one chain of neighbor updates, about 11 ms every few ticks, which is where its p95 comes from.

**Coordination** is the serial work around the parallel phases: collecting roots, building region tasks, ordering block events and committing. It is now smaller than the rule work in every workload but water_flood.

## Changes

1. **Skip random ticks where nothing reacts** (exact). The random-tick phase took 42 % of the clock workloads' time: every section of every ticking column drew three positions, though only crops react.
   - Sections now count their randomly ticking blocks, as the target version does.
   - Sections without any are skipped. Each section draws from its own stream, derived from seed, tick, column and section, so skipping one changes no other draw.
   - The oracle still runs every section, and the differential tests compare the two.
2. **Run small phases on the coordinator.** A phase attempt with at most `EngineOptions::inline_roots` roots (32) runs its tasks on the calling thread instead of waking workers; any order of tasks is a valid schedule. The differential tests run with `inline_roots = 0`, plus a separate case with a low threshold, so both paths are compared with the oracle.
3. **Fewer, larger pool jobs.** The pool runner used to post one job per task. Now up to `workers` threads, the calling thread included, take tasks from a shared index.
4. **Chunk packets in parallel.** Encoding a chunk packet costs 0.23 ms (dust connections, palettes, full sky light), so 32 chunks for a joining player took about 7 ms of the game thread. The server now encodes a tick's chunk packets on a pool of `workers - 1` threads plus the game thread. This scales linearly: 361 columns take 81 ms on one thread and 10 ms on eight (`chunk_bench`). It is safe because the engine does not run while packets are encoded; the encoders only read copy-on-write column snapshots and the published view.
5. **Background checkpoints.** See [the storage evaluation](STORAGE_EVALUATION.md): the game thread takes a snapshot in O(columns), and a writer thread encodes and writes it.

## Lower-risk parallel layers

The architecture names layers that can run in parallel without the in-tick ordering machinery:

| Layer | State |
| --- | --- |
| Storage I/O | Implemented: background checkpoints, plus a section cache that skips unchanged sections |
| Packet encoding and compression | Implemented: chunk packets are encoded in parallel. Each connection's compression and encryption already run on its own Asio strand, on the network threads |
| World generation | Not needed yet: the generator lays one stone layer. A real generator would run per column on the pool, with explicit ownership of decorations that reach into neighbors |
| Lighting | Not implemented: Circuit sends full sky light and has no lighting engine |
| Read-only pathfinding | Not applicable: the rules model no mobs |

## Limits

- The measurements cover the reference rules' workloads. They are not a comparison with the target version's tick times, and no claim is made about full survival servers.
- A connected machine that spans many columns runs in one region; its speed is that of one thread.
- `--profile-fixture` enables per-step timing (`EngineOptions::measure_tasks`), which adds two clock reads per root; the server runs without it.
