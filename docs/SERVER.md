# Network server

## Status

Circuit runs a playable world for Java Edition 1.21.8 (protocol 772) or 1.21.4 (protocol 769) on top of the headless engine. One server runs one version, chosen with `game-version`. The world is a flat stone floor at y = −61. The real client of either version can join in offline and online mode, build with the reference blocks, use levers, buttons, repeaters and comparators, and watch redstone, pistons, observers, hoppers, water and item entities run under the reference rules. Several players see each other and chat. Native modules and Java plugins can extend it through controlled services; see [the plugin API](PLUGIN_API.md).

Players play in creative or survival mode. In survival, placing uses up items, breaking takes the block's dig time and drops what the tool harvests, items are thrown and picked up, and chests, double chests and hoppers open with every click mode. Movement is checked against block shapes; players get hungry, take fall and void damage, die, drop their inventory and respawn. Inventories are simulation state; see [Survival and inventories](#survival-and-inventories).

With a world directory, the world is saved with checkpoints and an input log and survives crashes; Java Edition 1.21.8 worlds can be imported and exported. See [persistence](PERSISTENCE.md). Mobs, eating and crafting are not implemented; see [Not supported](#not-supported).

## Running

```bash
xmake run circuit-server --serve --offline --port 25565 --world "$PWD/worlds/main"
xmake run circuit-server --serve --config "$PWD/server.conf"
```

`--offline` sets `online-mode=false`, and `--world` sets `world-directory`. The server stops on SIGINT or SIGTERM. When it stops, it saves the world, disconnects every player with a reason and gives their connections up to two seconds to drain. It also stops by itself, with a non-zero exit status, when the world cannot be written.

The configuration file holds `key=value` lines; `#` starts a comment. Unknown keys and invalid values are errors.

| Key | Default | Meaning |
| --- | --- | --- |
| `bind-address`, `port` | `0.0.0.0`, `25565` | Listening address |
| `game-version` | `java-1.21.8` | Version bundle: `java-1.21.8` or `java-1.21.4`. Clients of another protocol are refused at login |
| `online-mode` | `true` | Require session verification. See [Identity](#identity) |
| `allow-flight`, `difficulty` | `false`, `easy` | Whether survival players may hover; `peaceful`, `easy`, `normal` or `hard` (how far players starve, peaceful regeneration, and how readily fire spreads); the world takes it at every start |
| `session-server` | `https://sessionserver.mojang.com` | Session service for online mode; plain `http` only on loopback |
| `auth-timeout-ms` | `5000` | Deadline for one verification |
| `max-players`, `max-connections` | `20`, `256` | Players in the game; open sockets of any kind |
| `view-distance`, `simulation-distance` | `6`, `4` | Chunks loaded and sent around a player; chunks simulated around a player (at most 8) |
| `pause-when-empty-seconds` | `60` | Seconds without players after which the world stops ticking until a player joins; `0` or less never pauses |
| `compression-threshold` | `256` | Packets of at least this size are compressed; `-1` disables compression |
| `network-threads`, `workers` | `2`, `4` | Asio threads for connections; engine worker threads |
| `login-timeout`, `keep-alive-timeout` | `30`, `30` | Seconds |
| `max-queued-bytes` | 16 MiB | Unsent data per connection before it is closed as too slow |
| `motd`, `seed`, `floor-y` | | Status text; seed and flat floor height of a new world (a saved world keeps its own) |
| `game-rule.<name>` | none | The value a game rule has in a new world (a whole number, or `true` and `false`; a saved world keeps its own), e.g. `game-rule.spawnRadius=0` |
| `world-directory`, `autosave-ticks`, `log-sync-ticks` | none, `6000`, `20` | Saved world and its checkpoint and log-sync intervals; see [persistence](PERSISTENCE.md) |
| `plugin`, `plugin-permissions.<id>` | none | A native module to load (repeatable) and its permissions; see [the plugin API](PLUGIN_API.md) |
| `java-bridge`, `java`, `java-plugin-class`, `java-plugins`, `java-permissions`, `java-max-lag-ticks` | none, `java`, none, none, `world.read`, `200` | The Java bridge; see [its guide](../modules/java-bridge/README.md) |

Setting the environment variable `CIRCUIT_TRACE_PACKETS=1` logs every serverbound play packet.

## Design

**Threads.** Each connection runs on an Asio strand. Its protocol state machine covers handshake, status, login, configuration and play, with framing, compression and encryption.

The game runs on one thread at 20 ticks per second, using the engine's tick clock:
- **Inputs:** network threads only enqueue joins, decoded intents and departures. The game applies them at the start of the next tick, in arrival order.
- **Tick:** the game turns the inputs into engine commands and advances the engine once.
- **Output:** it then publishes block changes, entity movement and chunk views to each player.

Players never touch engine state directly.

**Authority.** Every player action is validated before it becomes a command:
- **Movement:** finite coordinates inside the world border; at most 10 blocks per packet; only into delivered chunks; checked against block shapes (see [Movement and vitals](#movement-and-vitals)). Refused moves are corrected with a teleport, and non-finite ones are kicked.
- **Reach:** blocks within the interaction range plus 1 of the eyes, measured to the nearest point of the block: 6 blocks in creative (range 5), 5.5 in survival (range 4.5). An open container stays usable up to 4 blocks further.
- **Inventory:** creative slots 0–45 with known items, at most the stack's size, with components that pass the checks of [item components](COMPATIBILITY.md#content); a refused stack is logged and the whole window is sent again. Clicks only in the window the player has open.

**Block actions.** Clicks and creative breaking become the commands `PlayerUse` and `PlayerBreak`. The rules resolve them when they are applied, in admission order, against the state the earlier commands left. A player's actions therefore mean the same however they fall into ticks: a block placed and then built on, or a lever placed and then used, gives the same world whether the packets arrive in one tick or several. Admission checks only what the world does not decide:
- the held item's block state, oriented by the player and the clicked face;
- which of the two possible positions, the clicked block or its neighbor, is within reach and free of players.

When the command is applied:
- **Use:** a lever, button, repeater, comparator, door, trapdoor or fence gate is used (iron doors and trapdoors are not), unless the player sneaks while holding an item. A composter takes a compostable held item or gives its bone meal when ready; players within 64 blocks get the composting level event (`level_event` 1500, with 1 when a layer was added), as from both official servers (`composter.js`: the same levels, held stacks, events and comparator readings on both versions).
- **Placement:**
  - the block replaces the clicked block if that is air or water, otherwise it goes next to it;
  - the target must be air or water;
  - dust, repeaters and comparators need a solid block below, and levers and buttons a solid block to attach to; a redstone torch goes on the side of the clicked block, or on top of it when the top or bottom was clicked, and needs its support there; pressure plates need a block below to stand on; a door needs a sturdy top below it and room for its upper half, and takes its hinge as both official servers do: away from a door of its kind on one side only, else toward the side with more full blocks, else toward the half the click hit (left for the middle);
  - an observer's face looks the player's way; a trapdoor on a side goes in the half the click hit; wheat seeds need farmland;
  - torches go on the side of the clicked block or stand on its top, lanterns hang under a clicked bottom or stand, ladders hang on a clicked side, carpets, flowers and saplings rest on the block below; each only where its support holds it, replacing water (lanterns and ladders are waterlogged); sunflowers, lilacs, rose bushes and peonies need soil and room for their upper half; furnaces, smokers, blast furnaces, lecterns, beehives, ender chests and chiseled bookshelves face the player, barrels look back along the player's view, shulker boxes out of the clicked face, a beacon as it is with its block entity's levels 0 and the item's name, and jukeboxes, brewing stands and enchanting tables as they are, each with an empty block entity (an item with components, such as a named jukebox, places nothing: the block entity would not keep them); signs and banners hang on the clicked side of a solid block or stand turned to the player in sixteen steps of their yaw, heads hang on the clicked side or stand turned away, and beds lie with their foot where clicked, facing the player's way, and their head ahead, which must be free;
  - TNT placed where redstone reaches it is primed at once;
  - a chest joins a neighboring single chest as the official server does: next to one of the same facing, clockwise first, unless the player sneaks; when sneaking, the chest whose side was clicked, taking its facing.
  - building blocks place the block of their item as both official servers do: full blocks without properties (not spawners, beacons, sponges or test instance blocks), soul sand and mud as they are; logs and other pillars along the clicked face's axis; carved pumpkins, jack o'lanterns, glazed terracotta, looms, stonecutters and end portal frames facing the player; end rods and lightning rods out of the clicked face; stairs facing the player's way, and stairs and slabs in the top half for a click on a bottom face or in the upper half of a side; a slab clicked on its free half, or placed into a slab of its kind, becomes a double slab; fences, panes, bars, walls and stairs take their shapes from their neighbors; all are waterlogged in a water source; grass blocks, podzol and mycelium are snowy under snow; snow layers stack, a layer more for snow clicked on a layer's top or placed into it, up to eight. Blocks go into water and lava as into air, replacing them; neither can be mined. A single snow layer is replaced by any block placed at it. The client reports where its click hit the block. Buckets act on the use of the item that follows the click, along the player's view with the rotation the client sends: an empty one takes the first fluid source on it before the clicked block, a filled one pours into the clicked block or beside it (see [the simulation core](SIMULATION.md), Buckets).
- **Flint and steel and fire charges** (client/fire_items, both versions identical): fire beside the face used where it can stay (soul fire on soul sand), campfires, candles and candle cakes lit, TNT primed; flint and steel wears by one and breaks at its durability, a fire charge is used up, neither in creative mode, and a use that does nothing costs nothing.
- **Shears** (client/shears_items, both versions identical): pumpkins carved (facing the face used, or from above the player) with their four seeds, full beehives and bee nests emptied of three honeycomb; cobwebs, leaves, wool, vines and glow lichen dug at the shears' speeds; every block broken wears them, none in creative mode.
- **Books** (client/books, both versions identical): a book and quill in a hotbar slot or the off hand takes the pages the client edits, kept as sent (100 pages of 1024 code units at most; more, or a title of more than 32, fails to decode and closes the connection), and signing makes a written book with the title, the player as author, generation 0 and the pages as plain text; a written book is not edited, and using one opens it for reading.
- **The swap key** swaps the main hand's and the off hand's stacks (not for spectators).
- **Knowledge books** (client/knowledge_books, both versions identical): using one gives the recipes its recipes component names, as `/recipe give` does, when every one is a recipe (one that is not gives none); it is used up outside creative mode, also when it gives nothing.
- **Breaking:** any block but air and moving pistons; a piston head takes its base along.

A refused action is answered with the current state of the affected blocks, or, for a command refused when applied, restored by the client when the action is acknowledged. Every block action is acknowledged with its sequence number.

**World delivery.**
- **Chunks:** encoded from copy-on-write column snapshots: paletted block sections, plains biome, heightmaps (below) and each section's block and sky light (see [light](SIMULATION.md#reference-rules-v10)); sections that are dark are marked empty, and the section above the world has full sky light. At most 32 chunks per player per tick, nearest first.
- **Heightmaps:** computed from the blocks, as both official servers send them: WORLD_SURFACE (the highest block that is not air) and MOTION_BLOCKING (the highest that is solid or holds a fluid), and for 1.21.8 clients also MOTION_BLOCKING_NO_LEAVES (the same without leaves). Which states count follows Circuit's rules from public collision shapes (solid by the size of the collision box, with families that are always or never solid), matching a report of every state from both official servers; clients use MOTION_BLOCKING to show rain. For an official world imported through Anvil, all three heightmaps of a chunk with 35 test columns were identical.
- **View and simulation:** as in the target versions, each player has two chunk tickets. A loading ticket of level 31 over the view distance the client asked for (at most `view-distance`) loads those chunks, and two rings beyond them at levels 32 and 33, without simulating them. A simulation ticket of level 31 − `simulation-distance` at the player's chunk simulates what is loaded: entities within the simulation distance, blocks one chunk further. Every chunk of the view is sent, and chunks one beyond it stay shown while loaded. The spawn chunks keep a start ticket of level 32 − spawnChunkRadius (30 by default, none at 0), which follows the game rule in the tick it changes. See [chunk levels](SIMULATION.md#reference-rules-v10).
- **Block states:** every displayed property is rule state, including dust shapes, lever mounting and repeater locks, so clients see the state the rules hold.
- **Time:** as on both official servers, a `set_time` packet carries the world age, the day time and whether it advances (doDaylightCycle). It is sent on joining, to every player before each tick whose number is a multiple of 20 (after the commands that come with it), and at once when `/time` changes the time; changing doDaylightCycle sends nothing until the next one.
- **Weather:** as on both official servers, the rain and thunder levels are sent (game events 7 and 8) in each tick they change, and the start or end of rain (events 1 and 2, then both levels) when the rain level passes 0.2; a player who joins while it rains gets the start of rain and both levels. A segment-by-segment comparison of 16 `/weather` commands (and a doWeatherCycle change) and their 1,348 replies and events, including every level value, was identical with both versions.
- **Light updates:** light follows the blocks of the previous tick, as on the official servers; each tick, the sections whose light changed are sent as light updates to every player who has the chunk. The unmodified clients of both versions hold the same light as with the official servers (14 positions around a lit lamp and an overhang, also after joining again).
- **Updates and entities:** block changes in a tick become block updates for every player who has the chunk. Item entities, falling blocks (whose spawn carries their block state) arrows and snowballs (without an owner), minecarts and boats, and primed TNT (followed by its fuse, entity data index 8, which clients count down themselves; the official servers send it again each tick) are spawned, moved and removed from the engine trace. Entities are shown as they stand at the end of the tick that spawned them, after their first move; the official servers send the spawn before it. Players within 64 blocks of an explosion get it (its center, the explosion_emitter particle and the explosion sound; no knockback, since explosions do not push players yet).

## Survival and inventories

`/forceload add <x> <z> [<x> <z>]`, `/forceload remove <x> <z> [<x> <z>]`, `/forceload remove all` and `/forceload query [<x> <z>]` mark chunks of the overworld as force-loaded, as in the target versions: block coordinates (`~` for the player's own) name the chunks, at most 256 per command, and feedback uses the official translation keys. Each marked chunk is a forced ticket of level 31 that persists in the world. `/gamerule <rule> [<value>]` queries or sets one of the version's game rules, which are world state ([game rules](SIMULATION.md#reference-rules-v10)). It reads its input as the official servers do and answers with the same text components, including the error and the context line of a refused command; 45 commands gave identical replies on both versions. `/time set <time>|day|noon|night|midnight`, `/time add <time>` and `/time query daytime|gametime|day` set and query the world's day time the same way (a time is a number with the unit `d`, `s` or `t`); 59 of them gave the same replies and `set_time` packets as the official servers of both versions. `/weather clear|rain|thunder [<duration>]` sets the weather for a duration of at least one tick, or for the kind's default. `/gamemode survival|creative|spectator` switches modes. `/kill` (or `/kill <own name>`) kills the player in any game mode, with the official damage type, death message and feedback. Inventories belong to the simulation: every change is a command the rules apply (see [the simulation guide](SIMULATION.md#tick-structure)), so it is logged, replayed and checked for item conservation like the world.

- **Placement:** uses up the item; a water bucket leaves an empty bucket.
- **Digging:** the server follows the target version's destroy progress for the block, the held tool, the ground and water. A finish is accepted once the progress since the start reaches 70 % (network delay); one that comes too early completes when the progress reaches the whole block. A finish for another block, or without a start, is refused.
- **Drops and tools:** a broken block drops what the tool harvests, and a container drops its contents. With the official data pack, blocks without rules of their own drop from their loot tables (silk touch included), and random counts, chances, table bonuses and fortune roll from each table's random sequence as on the official servers. Tools wear by one per block and break at their durability.
- **Crafting:** with the official data pack, the player's 2x2 grid and crafting tables craft with the pack's shaped, shapeless and transmute recipes, stonecutters cut by its stonecutting recipes, and smithing tables upgrade and trim by its smithing recipes, with every click mode; the external `craft-loot.js`, `craft-table.js`, `stonecutter.js` and `smithing.js` scenarios give the same windows as both official servers. Twelve special recipes, all of the official data pack's, are made too (`special-a.js`, `special-b.js`, `crafter-special.js`, `fireworks-a.js`, `fireworks-b.js`, `crafter-fireworks.js`, `special-c.js`, `special-d.js`, `crafter-special2.js`, `map-extend.js`, `map-ids.js`, `map-extend2.js` and `crafter-map.js`, both official servers): repairing (two of one damageable item: both durabilities and 5 % of the most, and only their curses), armor dye (the dyes' colors mixed with the item's), banner copying (the patterned banner stays in its grid slot; a crafter throws it out after the copy), shield decoration (a shield without patterns takes a banner's patterns and color), firework stars (one gunpowder, dyes and at most one shape item, diamond and glowstone dust), firework rockets (one paper, one to three gunpowder and stars: three rockets), star fades (a star and dyes), book cloning (a written book of generation 0 or 1 and books and quills: as many copies a generation later; the written book stays in its grid slot, and a crafter throws it out after the copies), map cloning (a filled map and empty maps: one more of the filled map than there were empty maps), map extending (a filled map whose data exists, below the largest scale and locked or not, amid eight paper: the map marked to be zoomed, which becomes a new map of the next scale as it is taken, with the next map id; a shift-click makes a second such map that nothing holds, so it uses two ids, and a crafter throws the new map out), tipped arrows (eight arrows around a lingering potion: eight with its contents) and decorated pots (bricks or sherds in the middle cells of the top row, the sides and the bottom row: a pot decorated with them as its back, left, right and front; four bricks, its default, give a plain pot); a crafter's window shows what they make. Joining clients receive `update_recipes`: the item property sets of the cooking and smithing recipes and the stonecutter's recipes in the official order (by id path, then namespace; equal to both official servers' packets). Recipes of several namespaces match and are numbered in the recipe book in that order too (`ns-crafting.js` and `ns-book.js` with a test pack, both official servers): a grid or a furnace takes the first recipe in it that accepts its items, the special ones included. A recipe placed from the book at a crafting table is the exception, as on both official servers: the table makes the placed recipe until its grid next changes (a click that leaves the grid alone keeps it, one stack taken out and put back does not), with doLimitedCrafting off and on, so a shift-click makes it once and stops where the first recipe makes another item; the own window makes the first recipe, placed or not (`ns-place.js`, `ns-place2.js`; in the official pack the two rocket recipes take the same grid, giving the same rockets, and so do the two decorated pot recipes, giving the same pot).
- **Items:** `Q` throws one item from the selected slot and `Ctrl+Q` the stack, from the eyes along the look. Players pick up item entities whose box touches theirs, grown by one block sideways and half a block up and down, once their pickup delay has run out; the client shows the pickup.
- **Experience:** experience orbs appear to clients (on 1.21.4 by their own packet with their value, on 1.21.8 as entities whose value follows as entity data). Orbs drift toward the nearest player within 8 blocks; a player whose box, grown as for items, touches one takes one of its orbs every 2 ticks and gains its experience, and the client shows the pickup and the player's experience (`set_experience`, also on joining). A protocol-client scenario of orbs around a player (32 pickups, removals and experience updates, the joining one first) gives the same as both official servers, to the float of the progress bar. The rules know where each player is: the server sends a player's position whenever it changes.
- **Windows:** using a chest, a double chest, a barrel or a hopper opens a `generic_9x3`, `generic_9x6` or `hopper` window, unless a solid block lies above the chest (a barrel opens under one); a crafter opens a `crafter_3x3` window (its grid, the inventory and the result it would make; its disabled slots and triggered state as properties; slot toggles enable and disable empty slots), a crafting table a `crafting` window, a smithing table a `smithing` window, a grindstone a `grindstone` window, a loom a `loom` window (its chosen pattern as its property), a brewing stand a `brewing_stand` window (its brew time and fuel as its properties), a beacon a `beacon` window (its payment slot; its levels and its two powers as its properties), and a stonecutter a `stonecutter` window, whose recipe buttons work and whose chosen recipe goes out as its property; a furnace, smoker or blast furnace opens a `furnace`, `smoker` or `blast_furnace` window, whose four properties (the fuel's remaining and total burn time, the cooking progress and its total) go out in `container_set_data` when they change. All seven click modes work in it and in the player's own window. Windows close when the container is removed or changes size, or the player moves out of range; closing returns the carried stack and the crafting grids. Each window's title is the translation both official servers send for it (`container.chest`, `container.chestDouble`, `container.barrel`, `container.hopper`, `container.repair` and so on; `titles.js`, `titles-lectern.js`, `enderchest.js`, `shulker.js`: the same for all twenty-two kinds on both versions), or the container's custom name. A shulker box opens a `shulker_box` window (type 20) of its 27 slots, unless something is in the way of its lid, and refuses shulker boxes (`shulker.js`: the same on both versions); broken, it drops one item with its contents (the `container` component), which gives them back when placed. An ender chest opens a `generic_9x3` window of the player's own ender inventory (`enderchest.js`: the same contents through another ender chest, a second player's own, and no window under a stone, on both versions). Chests (trapped chests too), ender chests, shulker boxes and barrels count the players viewing them (shulker boxes without rechecks); a barrel is open while anyone views it: every change of a half's count, and its recheck every 5 ticks while viewed, sends players within 64 blocks the half's lid event (`block_event`, event 1 with the count), and a trapped chest powers by its count; a protocol-client scenario of two players opening and closing a trapped chest, a double trapped chest and a chest (`openers.js`) gives the same power and the same events as both official servers. A player who leaves drops them where they stood; a dying player's window closes without a packet (the death screen replaces it), and the death drops them.
- **Synchronization:** as the target version does, the server keeps the client's view of its window. It takes the slots and carried stack the client predicted for a click as that view, and after each tick sends only the slots that differ. A click made on a stale state id, or one whose prediction cannot be read, gets the whole window; each window counts its own state ids (the own window's go on after another window closes, a container window's start at 1). As both official servers do (`window-sync.js`; both versions send the same packets and state ids for these), an item use that changes the stack it takes from (an empty map, a bucket filled or poured and a knowledge book used up from the main hand; an empty map and a bucket filled from the off hand) sends the whole own window in place of the slots that changed; with a chest open (an empty map, a bucket filled and poured) it comes before that window's changes. A use that leaves its stack as it was (a bucket at the sky, the uses of creative mode) sends only what else changed, and dropping from the held slot sends nothing for that slot, the client having changed it itself. Protocol 772 predicts stacks with hashed components, which the server does not compute: a predicted slot that holds components is sent again. Creative slot changes are not echoed. While another window is open, the client's view of its own window follows the player slots that window shows; closing it, the server sends only the own window's slots that differ from that view (an off hand changed meanwhile, say), and each stack a closing window puts back into the inventory (a carried stack, a crafting grid's items) first by its inventory index (`set_player_inventory`, with the stack as it is after that placement), as both official servers do (`close-probe.js`: the same packets on both versions). Each change a click makes to a crafting grid's slot (the own window's or a crafting table's) sends the result slot again, changed or not; a slot emptied by picking its stack up or throwing it, and one that keeps a remainder when the result is taken, changes twice. Closing the window sends the result only when it changed, as both official servers do (`own-grid-counts.js`, `table-grid-counts.js` and the close of `recipes-place8.js`); placing a recipe from the book does too, where the official servers send it again for each grid change the placement makes (the same window either way). The slot packets of each step of `special-a-counts.js`, `own-grid-counts.js`, `own-grid-counts2.js`, `own-grid-counts3.js` and `table-grid-counts.js` are the same as both official servers'. A window closed in the tick another opens sends what it put back and the own window's differences before the new window, as a tick apart.
- **Maps:** players carrying a filled map get its data packet (the whole map the first time, then each tick the markers that changed and the rectangle of pixels that changed), as both official servers send it. Each player's presence names the hotbar slot in their main hand, so the maps held in a hand explore once the levels ran (see [the simulation core](SIMULATION.md), Maps exploring).
- **Recipe book** (with the official data pack; client/recipes, both versions identical): every recipe with a display has the display id of its place among the recipe ids sorted (special recipes have none, but map extending, which no book shows), its group numbered by its first recipe, its category, its display (shaped and shapeless grids, ingredients as tags or items, items that leave a remainder with it, results with suspicious stews' effects, furnace, stonecutter and smithing displays, trims by pattern or before 1.21.5 by template) and the items it requires. A joining player gets the four books' settings and every recipe they know, still highlighted or not. The advancements that reward recipes unlock them when their criteria are met: an item that changed in the inventory (armor, main inventory, hotbar, off hand) matches, ten slots are filled, the first tick, the player stands in water, or the recipe is known; each completed advancement sends its new recipes, highlighted, with a notification unless the recipe shows none. Taking what a recipe made from a crafting grid, a stonecutter, a smithing table or a furnace's output gives the recipe first. A recipe the client saw loses its highlight, and the books' settings are kept; both, the known recipes and the advancements done are saved with the player. The official servers send the recipes unlocked in one tick in an order that varies; Circuit's follows the advancements' ids. Advancement packets are not sent (C9).
- **Placing recipes from the book** (client/recipes_place, both versions identical): a known recipe asked for in the open window (the own window while none is open; another window's id is ignored) fills the own window's or a crafting table's grid, or a furnace's, blast furnace's or smoker's input, from the hotbar and the main inventory (not the off hand, and only stacks without damage or components of their own). The grid's items go back first, the selected hotbar slot filled first; when they would not all fit, nothing happens. Once places one craft more than the grid's smallest stack of that recipe, as many as fit places as many crafts as the items allow, each item at most to its stack size (16 eggs, one milk bucket). Shaped recipes narrower or lower than half the grid are centered, and the cells of a recipe too big for the grid are left out (its items are still needed). With too little for one craft, the grid is emptied and the ghost recipe sent; a recipe of another kind (a cooking recipe in a crafting grid, a crafting or stonecutting recipe in a furnace) changes nothing when the items are there, and a crafting table shows no ghost of one. Cooking recipes of every furnace kind and campfires go into any furnace. Among several kinds of items for an ingredient the official servers' choice varies from run to run; Circuit takes the kinds in the order the inventory first holds them.
- **`doLimitedCrafting`** (client/recipes_limited, both versions identical): with the rule on, the own window's grid and crafting tables make only recipes the player's book knows, in creative mode too; special recipes are not limited (paper and gunpowder make rockets by the special recipe, which comes before `firework_rocket_simple` in id order; `rocket-order.js`, both versions identical), nor are stonecutters and smithing tables. A result already shown stays until the grid changes, when a recipe is learned or taken away, the rule is turned on or off or a click leaves the grid alone (an empty slot, stacks moved elsewhere, a number key), and it can still be taken, which gives the recipe back (`recipe-take.js`, at a crafting table and in the own window, both versions identical). The server tells the rules each player's crafting recipes when they join and whenever the book changes.
- **Beacons** (`beacon.js` in the external client tests: a 35-step scenario with two players, identical on both official servers and both versions; `beacon2.js`: a payment left in the window, a spectator, players flying far above, a beacon without levels removed and a named beacon; `beacon-dbg.js` for the game times of the sounds): a placed beacon sends its block entity data (`Levels` 0). Its window's payment slot takes one payment, which closing the window throws out, and `set_beacon` chooses its powers while the slot holds one, which it uses up, whatever its levels; a named beacon's window has its name as its title. On each game tick that is a multiple of 80, a beacon whose beam is open counts its pyramid; with levels it gives its powers to the players but spectators whose box reaches its range (10 blocks per level and 10 more on every side, then up by the world's height) as ambient effects for 9 seconds and 2 more per level, then plays its ambient sound. Its sounds (activate, ambient, deactivate, power_select; deactivate also when a beacon is removed, with levels or without) go to players within 16 blocks in the blocks category at volume and pitch 1.

The clicks were calibrated against the official 1.21.8 and 1.21.4 servers. The same 48-step mineflayer scenario gives identical windows, carried stacks and inventories on both servers and on Circuit. It covers every click mode, double chests, hoppers, the own window, thrown items and pickups. A second scenario, `craft-loot.js`, crafts in the own window (48 steps) and breaks 23 blocks with various tools on both official servers and on Circuit with the official data pack. The crafting windows are identical. The drops are identical wherever the block's loot table draws no random numbers; random rolls depend on the world seed, and were compared in recorded traces instead (see [the simulation core](SIMULATION.md)).

### Movement and vitals

- **Game modes and spectators** (`spectators.js` in the external client tests, both versions alike): `/gamemode` sends the abilities, the game mode event, the player list's new game mode (that entry alone) to everyone, then the abilities again. A spectator is seen by spectators only: those who are not see it go at once (on both official servers its invisibility came first in two of eight runs, when their entity tracker ran before its next move) and appear again when it leaves the mode; a spectator sees everyone. Its shared flags carry the invisibility. A spectator digs nothing (only the start is answered with the block), places and uses nothing, and picks nothing up, but opens a block's window, a chest's without opening its lid (the other windows by the same rule, but an ender chest's, a lectern's, a chiseled bookshelf's slots and a chest under a block that conducts; not recorded), whose slots, buttons, names and powers it cannot change. Attacking an entity takes its view (`set_camera` and a teleport to it; recorded with a player, other entities Circuit shows by the same rule), which it follows, its chunks with it, until the shift key goes down or the entity dies or goes; the spectator menu's teleport takes it to a player. It moves through blocks.
- **Shared flags and pose** (`spectators.js`): the shift key sets a player's shift flag (0x02) and, but for a spectator or a flyer, the crouching pose, to the player and to those who see them at the next entity update; 1.21.8 takes the shift key from `player_input`, 1.21.4 from the player command (its server ignores `player_input`'s). Sprinting's flag is not sent yet.

The server follows the target version's movement handling for every player but spectators:
- **Collision:** a claimed move is replayed from the last accepted position against the collision boxes of every block state, the same boxes and box collision items use in the simulation (the block registry; equal to both official servers' boxes for every state). The vertical axis moves first, then the horizontal axis with the larger movement, and a player on the ground steps up to 0.6 blocks.
- **Refused moves:** in survival, a move that ends more than 0.25 blocks away horizontally from the replayed one is refused, unless the player was already stuck in a block. In any mode, a move into a block the player was not already in is refused. Vertical differences are not compared, as in the target version.
- **Floating:** a survival player who neither sinks nor stands on or next to anything for 80 ticks is kicked with the client's "Flying is not enabled" message, unless `allow-flight` is set or the player levitates (`effects5.js`: not kicked on either official server).
- **Falls:** the distance fallen since the ground deals one point per block beyond the safe fall distance (3, one more per level of jump boost): on 1.21.8 with the move that lands, rounded down, on 1.21.4 without it, rounded up (`falls.js` and `attributes-order.js`: 5.5 blocks landing apart took 2 and 3 points, 6.3 blocks landing 0.5 blocks down 3 and 3, 4.4 landing 0.4 down 1 and 1, 9 blocks as a client lands 6 on both). Water and flying reset it; a slime block cancels the damage unless the player sneaks.
- **Hunger:** food, saturation and exhaustion follow the documented rules: jumps (0.05, sprinting 0.2), sprinting on the ground (0.1 per metre), moving through water (0.01 per metre), breaking blocks (0.005) and healing tire players in survival. Healing comes from saturation with full food (saturation/6 every 10 ticks) or from food 18 or more (one point every 80 ticks), in every game mode, up to the maximum health and while the `naturalRegeneration` game rule allows; without food players starve down to the difficulty's limit. Food comes back by eating (below) and with the saturation effect.
- **Eating and drinking** (`eat.js` in the external client tests, both versions alike, for the 18 kinds it eats; the other foods from minecraft-data and minecraft.wiki): holding use with food, milk, a potion or an ominous bottle in a hand starts a use that lasts 32 ticks (dried kelp 16, honey 40). Food is refused at full hunger in survival, but for honey and chorus fruit (recorded) and golden and enchanted golden apples and suspicious stew (minecraft.wiki); never in creative mode; never while the item cools down. The living flags (entity data 8: using an item, and the off hand, which stays set after the use) go to the player and those who see them when it starts and ends. The others within 16 blocks hear it in each tick that starts with a multiple of 4 ticks left, once more than a fifth has passed, and in its last (seven times in 32 ticks, once when let go after 10, twice when switched away after 16; eating at volume 0.5 or 1, drinking at 0.5; the volume and pitch are Circuit's own draws). Letting go and another hotbar slot end it (recorded), and so do another item in the hand, spectating and death. When it runs out the rules use the item up (`ConsumeItem`; not in creative mode) while the slot still holds that stack, and leave its bowl, bucket or glass bottle in its place or, with some of the stack left (not recorded), in the inventory, the selected hotbar slot first, thrown out without room. Then the player alone gets the finished use's event (9) and, in the order both official servers act: a suspicious stew's effects; a food's sound (category neutral) and a burp, to everyone within 16 blocks; a potion's effects (instant health and damage at once) and those its contents add; an ominous bottle's bad omen at its amplifier for 100 minutes, its particles hidden, and its sound; milk ending every effect, honey ending poison; a chorus fruit's teleport: up to 16 tries at random places within 8 blocks, let down onto the ground, the player staying at the first where it fits out of fluids (minecraft.wiki; Circuit's own draws, a position sent for each try that finds ground, where both official servers sent one to nine positions in a use and failed more tries than Circuit does, by rules not determined), entity event 46 and its sound where the player was, then a cooldown of 20 ticks for every chorus fruit, told when it starts and when it ends (recorded); the food's own effects in its order (recorded for golden and enchanted golden apples, spider eyes and pufferfish; the chances of raw chicken's, rotten flesh's and poisonous potatoes' from minecraft.wiki, drawn from Circuit's own random); its food and saturation (the saturation up to the new food; in creative mode too); the health packet, the living flags, then the slot. A use in progress and the cooldowns are not saved; a stack's own food, consumable, use remainder and use cooldown components and 1.21.8's potion duration scale are not read (each item eats as its kind by default).
- **Damage:** fall, starvation and the effects' damage hurt only survival players; the void (more than 64 blocks below the world) deals 4 points to every player but spectators. A hurt cooldown of 20 ticks lets only stronger damage through in its first 10 ticks, and only by how much it exceeds the last. Absorption takes damage first. As both official servers tell it (`effects-heal.js` in the external client tests: falls, starvation, magic and wither damage, both versions alike): the hurt player and those who see them get the damage event (the damage type's registry id) at once; the other players within 16 blocks hear `entity.player.hurt` (category player; Circuit draws the pitch itself), or `entity.player.death` for a lethal hit; the velocity follows at the next entity update, to the player and those who see them, as that of a player standing still. A fall that hurts is heard first as `entity.player.big_fall` beyond 4 points of damage, else `entity.player.small_fall`; the fall sound of the block landed on is not played. The health follows at the end of the tick, after the velocity of a fall and before that of the effects' damage.
- **Death and respawn:** at zero health the client shows the death screen with the target version's message (a translation key with the player's name as both official servers write it: a click suggests `/tell <name> `, a hover shows the player, in each version's form), everyone reads it, the player and those who see them get the death animation (entity event 3), and the inventory drops (a `PlayerDeath` command; items dropped below the world are lost). The body stays in the others' view, its health 0 and its velocity told at the next entity update; after the death animation it gives its last entity event (60) and goes from the others' view, and they from the dead player's (`player-data.js` in the external client tests: a player on the death screen, both versions alike; Circuit takes 20 ticks, the official servers' tick was not recorded). Asking to respawn brings the player back with full health and hunger, as both official servers do: the abilities, the respawn, the position, the spawn (twice), the operator level, the commands, the view's center and the inventory, then the player's first entity data, the attributes and the health (the official servers also send the difficulty, the world border and the time again, which Circuit does not); their client is told to remove the other players they still see before the respawn, and they appear to it again after; those who saw the player see the body go and the player appear again.
- **Where players appear:** a new player, a player who left dead, and a respawning player appear at the world spawn's center, or with the `spawnRadius` game rule (10 by default; Circuit takes at most 64) in a random column of the square that many blocks around it, standing on the column's highest block that stops movement, when its top is full and it holds no water (a column whose top is water or lava is passed over) (minecraft.wiki "World spawn"; `player-data.js`: within 10 blocks, not at the center, on both official servers, which draw the place at random; Circuit draws its own, and falls back to the center after 16 columns that do not do).
- **Operator level:** every player may run every command, so each gets the highest operator level (entity event 28) as both official servers send an operator's: on joining after the recipes, and on respawning after the spawn, each time before the commands.
- **Players' entity data** (`player-data.js`, both versions alike): a player's health (index 9), the skin parts the client shows (17, from its settings) and its main hand (18, left or right) go to the player and to those who see them at the next entity update when they change: the health after the health packet when the player's own tick changed it (the effects, hunger), the skin parts and main hand when the client's settings change them (the health that a move's fall changes goes before the health packet, as the next entity update comes first; not recorded). The living flags (8: using an item, the off hand) go at once when a use starts and ends (`eat.js`). A player who appears comes with them (and the effects' entries), and a new entity (a player who joined or respawned) sends its first data too: the player gets it with their effects on joining (on respawning at the next entity update), and those who see the player appear in that tick get it again after the appearance (and after the attributes a returning or respawning player appears with; a new player's come after both), as both official servers send it.
- **Status effects** (`effects2.js`, `effects3.js`, `effect-colors.js`, `effects4.js` and `effects5.js` in the external client tests; both versions alike, but for orders the official servers vary from run to run): `/effect` gives players the 39 effects of the registry and clears them, with the official parser and replies. An effect given again combines with the one a player has as on the official servers: a stronger level replaces it, the old one staying underneath to come back when the stronger ends if it lasts longer; the same amplifier lengthens it; a weaker, longer level goes underneath without a change shown; particles or the icon shown or hidden change it whatever its strength. Every level counts down each tick, those underneath too: one that runs out before the level above it ends is shown with no time left when that one ends, and the effect is removed in the same tick with any level still under it (recorded with two and three levels); an effect is sent again whenever its time left is a multiple of 600 ticks (recorded at 600, 1200 and 1800), and removed when it ends. The player gets each effect added (marked new), changed and removed at once; the entity data they decide follows to the player and to whoever sees them in the next tick, as both official servers send it 25 ms or more after the packets (the 1.21.8 server timed: 80 ms after a command's, 50 ms after one sent in a tick; Circuit sends a command's a tick, 50 ms, after it): the invisibility and glowing flags (with the other shared flags: above), a particle for each effect that shows particles (its color, or the particle of its own of the omens, wind charged, weaving, oozing and infested), and whether all of those are ambient. Effects are saved with the player and sent again on joining, before the health (they count down from the next tick); a respawned player has none. The effects that heal, hurt or feed act as on both official servers (`effects-heal.js`), by the time their shown level has left before each tick counts it down: instant health heals 4 and instant damage hurts 6 (magic), doubled per level, in every tick they last (the duration `/effect` gives them counts ticks); regeneration heals 1 below the maximum health when that time is a multiple of 50 ticks, halved per level; poison hurts 1 (magic) above 1 health every 25 ticks and wither 1 (wither) every 40, halved per level, the hurt cooldown keeping out hits that come too soon; hunger tires a survival player by 0.005 per level each tick; saturation gives 1 food and 2 saturation per level (the saturation up to the food). Creative and spectator players take no damage from them. Absorption ends once its absorption is used up (`eat.js`: with poison's damage), and an omen (bad, trial or raid) that comes plays its sound to the player and the others within 16 blocks, by `/effect` too (`eat.js`). The official servers list a player's effects in an order that varies from run to run, and players' entity data of one tick in an order of their own; Circuit lists effects in id order and players in the order they connected.
- **Attributes** (`attributes.js`, `attributes-order.js`, `attributes-join.js` and `dig-effects.js` in the external client tests; both versions alike but for the attributes' ids and fall damage's rounding): a player has the attributes the official servers give them (on a first join the movement speed and the block and entity reach, then those an effect changes), each with a player's base and its modifiers in the order added, kept across respawns and saved with the player. Creative mode reaches 0.5 blocks further to blocks and 2 to entities; sprinting is 30% faster; speed, slowness, haste and mining fatigue change the movement or attack speed (20%, -15%, 10% and -10% of the total per level), jump boost adds a block of safe fall distance per level, health boost 4 maximum health, absorption 4 maximum absorption, luck and bad luck one luck either way. Strength and weakness change the attack damage (by minecraft.wiki: 3 and -4 per level; the official servers send no attribute for them, so this is not observed). An effect's modifier is added again, moving to the end of its attribute's list, whenever its shown level is given, changed, lengthened or comes back, but not when the effect is only sent again. The attributes changed in a tick go to the player and to whoever sees them after the entity data of the next tick, each with all its modifiers, and a player who appears to another comes with all of theirs. A first join sends them after the health; a rejoin or a respawn sends all of them before the health (without modifiers after a respawn), those who see the player get them a second time in that tick, and creative mode's reach follows. The server uses the maximum health (regeneration, health above 20 kept across a rejoin, and the health cut when the maximum falls, before its packet), the maximum absorption (the absorption effect raises the absorption to 4 per level whenever its shown level is given, changed, lengthened or comes back; recorded when given and lengthened; absorption takes damage first, is kept across a rejoin, is cut when the maximum falls and is entity data for the player and those who see them), the safe fall distance, and haste, conduit power and mining fatigue in digging (20% faster per level of the stronger of haste and conduit power, 0.3, 0.09, 0.0027 or 0.00081 times by mining fatigue's level, the documented values; recorded with haste 0 and 1, conduit power 1 and mining fatigue 0, as both official servers break a block a client finished early). The movement and attack speed, the reaches and luck only reach the client: Circuit's movement checks do not use the speed, and it has no attacks or rolls with luck. The official servers list a packet's attributes in an order that varies from run to run; Circuit's follow their ids.

The client is told health, food and saturation when they change, as the target version does. On joining they follow the inventory, the position and the recipes the first tick unlocks, and the experience follows them, as both official servers send them (`join-order.js`, both versions identical): a client that counts from the first health packet has read the inventory and those recipes. Two black-box scenarios (`vitals.js` and `collision.js` in the external client tests) give identical results on the official 1.21.8 and 1.21.4 servers and on Circuit: a wall correction, fall damage, regeneration with draining saturation, a deadly fall with its drops, respawning, void damage against regeneration, the death messages, the floating kick, and moves against chests, repeaters, a hopper's bowl and full blocks. Everyone but the newcomer is told that a player joined (`join-message.js`, both versions).

## Identity

`online-mode=true` performs the documented key exchange: a 1024-bit RSA key, AES-128/CFB8 in both directions, and the login hash. The server then asks the session service whether the player joined.
- **Verified:** the profile id, name and properties (skins) come from the service.
- **Default deny:** when the service does not confirm the join, cannot be reached in time, or answers malformed data, the login is refused.
- **TLS:** certificates and host names are verified.

`online-mode=false` admits offline identities: the name-based UUID of `OfflinePlayer:<name>`, labelled unverified. The log states which kind each player has. Offline mode does not exempt an operator from the Minecraft terms.

## Protocol data

Numeric protocol data is compiled from public documentation, and every table names its source.

| Data | Source | Tool |
| --- | --- | --- |
| Packet ids | minecraft.wiki "Java Edition protocol/Packets", revision 3258009 (1.21.8) and 2938097 (1.21.4) | `tools/extract_packet_ids.py` |
| Block states, items, entity types | PrismarineJS minecraft-data (MIT) at commit `095709f3`, which the wiki's protocol FAQ points to | `tools/compile_content_tables.py` |
| Registry entries, their data and the biome tags 1.21.4 needs | minecraft.wiki pages cited in `src/server/registries.cpp` | by hand |
| Item component schema and static registry sizes | PrismarineJS minecraft-data `protocol.json` and registry tables at the same commit | `tools/compile_components.py` |
| Map colors of block states | What held maps drew on both official servers for every state Circuit's probe placed (`tests/fixtures/maps/colors-*.txt`), with PrismarineJS minecraft-data's collision shapes at the same commit for the waterlogged rule | `tools/compile_map_colors.py` |

| Field layouts | minecraft.wiki protocol pages at the same revisions | by hand, in `src/server/wire.cpp` |

Two consistency checks guard these tables:
- **Packet ids:** where the two public sources name the same packet (83 packets), their ids agree. Per state and direction they list the same number of packets for 1.21.8.
- **1.21.4 packet count:** minecraft-data lists two more serverbound configuration packets for 1.21.4, `custom_report_details` and `server_links`. These are clientbound packets in the wiki's tables, so the server follows the wiki. The eight ids both sources share agree.
- **Block states:** every block's state count matches its properties, and every state id round-trips through its notation.
- **Registries and game rules:** every synchronized registry has the same entries as the official server's configuration, and each bundle's game rules are the official server's `/gamerule` list (`tests/fixtures/registries/`, observed 2026-10-10). The check found the four element paintings missing from the painting table, now added. The official servers also send registries Circuit does not: enchantments (their definitions need item and enchantment tags), and in 1.21.8 dialogs and the game-test registries.

**1.21.4 differences.** The 1.21.4 wire protocol differs from 1.21.8 in what the server uses:
- **Chunk data:** heightmaps are an NBT compound, and paletted containers carry their data-array length.
- **Registries:** the cat, chicken, cow, frog, pig and wolf-sound variants are not synchronized, "Dennis" is not yet a painting, and the jukebox songs lack Tears and Lava Chicken.
- **Tags:** its wolf variants need the `is_badlands`, `is_jungle` and `is_savanna` biome tags, which the server sends.

The real client exercises the rest.

Each version bundle names its registry set (`circuit-server --compatibility` prints it). Clients that report the vanilla data pack receive registry entry names only: 17 registries in 1.21.8 and 11 in 1.21.4, including trim materials and patterns, banner patterns, goat-horn instruments and jukebox songs, whose definitions refer to no tags. Their entries are numbered as the official servers number them (by name); banner patterns were numbered in another order before this release, so a banner with patterns saved by an earlier Circuit world shows other patterns. With the official jar's data pack (`vanilla-server-jar`, see [data packs](DATA_PACKS.md)) they also receive the enchantments and every tag of the registries Circuit numbers. Clients that do not, such as protocol libraries, receive a documented minimal set with data: overworld, plains and the `chat` chat type.

## Not supported

- Mobs, combat between players and armor protection.
- Status effects' consequences beyond their attributes, absorption, digging and the effects that heal, hurt or feed: resistance and slow falling change nothing (fall damage is taken in full), fire resistance and water breathing (fire and drowning are not modeled either) or the omens (but the sound each makes when it comes) and the effects that act on death or when hurt; only players have effects; of the attributes effects change, the movement and attack speed and luck only reach the client. The fall after levitating hurts as on both official servers (2 points on 1.21.8 and 3 on 1.21.4 after rising about 5.2 blocks), but on 1.21.4 the health regenerated after it differs from the fourth heal, 0.33 points where the official server healed 0.5 (`effects-lev.js`).
- Crafting without the official data pack.
- Item use other than placement, eating and drinking, water and lava buckets, bone meal, maps, flint and steel and fire charges (other buckets, tools on blocks, weapons), use sounds but eating's and drinking's, and item cooldowns but the chorus fruit's.
- Where a player appears around the spawn is drawn from Circuit's own random, not the target version's. Death drops spread in a fixed pattern instead of at random.
- Swimming and crawling poses, climbing, elytra flight and vehicles: their movement is checked like walking.
- World generation is a flat floor.
- Saving is limited to what [persistence](PERSISTENCE.md) describes. Checkpoints are written in the background; the game thread takes a snapshot and syncs the start of a new log segment.
- Signed chat: chat is relayed as system messages. Commands are `/help`, `/players`, `/tp [<own name>] <x> <y> <z>` (with the own name also `<yaw> <pitch>`; whole numbers for x and z are the middle of their block, as on the official servers), `/gamemode survival|creative|spectator`, `/forceload`, `/gamerule`, `/time`, `/weather`, `/kill` (the player themselves), `/summon <entity> <x> <y> <z> [{...}]` (the entities the rules summon, at absolute coordinates, with the data tags fixtures take), `/setblock <x> <y> <z> <block>` (a block state with every property, at whole or `~` coordinates, placed with normal updates and an empty block entity), `/fill <x1> <y1> <z1> <x2> <y2> <z2> <block>` (replacing: every block of the box that differs, set as `/setblock` sets one, x fastest, then z, then y; at most 32768 blocks, with the official replies), `/recipe give|take <player> <recipe>|*` (the recipe book's recipes; the reply counts those named, every recipe for `*`, once any changed, as on the official servers), `/xp` or `/experience` (`add`, `set` and `query`, with the official replies), `/effect give <targets> <effect> [<seconds>|infinite] [<amplifier>] [<hideParticles>]` and `/effect clear [<targets>] [<effect>]` (players by name, `@s`, `@p`, `@a` and `@e`, with the official parser and replies; an instant effect's seconds count ticks) and `/tps`, with no command-tree suggestions and no permission levels. Every player may use every command: a very large randomTickSpeed stalls the tick, as it does on the official servers, where only operators can set it.
- Display gaps: block entity data is sent only for a newly set beacon (its levels, 0), so moving pistons are not animated. Other blocks and entities are out of scope.
- **Other versions:** 1.21.8 and 1.21.4 only. Anvil import and export are defined for 1.21.8 worlds only. A world directory belongs to one bundle; `--migrate-world` copies it to another bundle when both run the same rules.
