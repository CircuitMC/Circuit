# Headless simulation core

## Status

The Part I core runs headless: shared contracts, a set of reference rules, a sequential scheduling oracle, and a region-parallel runtime checked against the oracle. The oracle shares gameplay rules with the runtime; it checks scheduling equivalence, while external reference observations and hand-derived expectations check the rules themselves. The [network server](SERVER.md) and [persistence](PERSISTENCE.md) are built on it.

The rules are **circuit-reference-rules-v12**. They are Circuit's own definitions, written from public documentation and from traces recorded by an instrumented server outside this repository.

Two version bundles run them: `java-1.21.8` and `java-1.21.4`. 1.21.8 has 225 traces and 1.21.4 has 220 recorded on the unmodified server (1.21.4 lacks the tntExplodes game rule, so `tnt_explodes_disabled` and `dispenser_tnt_rule` are 1.21.8's only, `fire_basics` shows that 1.21.8's fire acts only near players, and `lava_fire` turns on allowFireTicksAwayFromPlayer, which 1.21.4 lacks):
- 1.21.8 traces are in `tests/fixtures/harness/`;
- 1.21.4 traces are in `tests/fixtures/harness-1.21.4/`.

The 1.21.4 traces equal the 1.21.8 traces apart from their headers (the 1.21.8 fire traces turn on allowFireTicksAwayFromPlayer, which 1.21.4 lacks, so that fire acts away from players as on 1.21.4), but `entities_in_lava` (lava reaches entities at the start of their ticks on 1.21.4 and after their moves on 1.21.8, `LavaContact`) the fourteen random-tick traces (1.21.4 runs random ticks only near players, `RandomTickRange`) `anvils_falling_far` (a falling anvil wears by its fall before the landing move on 1.21.4, `FallDistance`) and those of experience orbs (they bounce and drag otherwise on 1.21.4, and fall and move out of blocks as items do there, `OrbMotion`), differences the bundles declare (`tests/fixtures/version-differences.txt`). All 445 pass on both the parallel runtime and the oracle.

The compatibility table is part of the version bundle (`src/contracts/version.cpp`). `circuit-server --compatibility` prints it. Each row states a target tier, a claimed tier, the evidence source, and its limitations:

- **L0 exact**: a row claims L0 only when target-version traces pass and no gap is known. "Not covered" lists aspects that no trace exercises.
- **L2**: every other row claims L2 and lists its gaps, including behavior not yet compared with the target version.

The tiers are defined in the architecture: L0 exact, L1 region-equivalent, L2 declared deviation.

## Tick structure

Logical time advances by one per executed tick. Each tick runs these phases in order (the target version's order). Within a phase, work is a sequence of *roots* in a fixed serial order. Immediate reactions (neighbor and shape updates) finish inside their root.

**Levels.** A world has levels: the overworld, the Nether and the End.
- **Own state:** each level keeps its own columns, scheduled ticks, block events, block entities and entities. Positions mean nothing outside their level, and rules never reach into another level.
- **Commands and tickets:** every command, and every ticket, names its level.
- **Order:** the command phase runs once, for all levels. Then each level runs the phases below, the overworld first, then the Nether, then the End (minecraft.wiki "Tick"): its scheduled ticks where columns are loaded, its chunk stage, and the rest where columns are loaded after it.
- **Counters:** tick sub-orders, block-event positions and block-entity creation order count per level; entity ids count over all levels.
- **Random streams:** each level has its own level random and its own random-tick position generator (below).
- **Not yet reachable:** only the overworld is generated and reachable by players. The other levels exist for the engine, its tests and the formats; they have no rules of their own yet (C7).

| Phase | Roots in serial order |
| --- | --- |
| commands | admitted commands by admission id |
| block ticks | scheduled block ticks due now in block-ticking chunks, by (due, priority, sub-order), at most 65,536 |
| fluid ticks | scheduled fluid ticks, same order and limit |
| chunks | the level's tickets whose lifetime is over go, then one root applies its chunk-level changes |
| random ticks | chunks whose random ticks run (below) in coordinate order, then sections bottom to top |
| block events | the level's FIFO, including events queued while it drains; an equal event is queued once, and an event runs only if its block is still there; events in chunks that do not block tick stay queued in order and run once the chunk ticks (block_event_rings) |
| entities | entities in entity-ticking chunks, ascending id, at most once per tick, while the level is awake |
| block entities | block entities in block-ticking chunks, ascending creation order, while the level is awake |

Commands are external inputs applied between ticks, so they observe the previous tick's time. A delay that a command starts counts from that time.

Commands apply serially in admission order, each with its immediate reactions, so a command sees everything the earlier commands of the tick changed. Player actions use this: `PlayerUse` (a click on a block face) and `PlayerBreak` decide what to use, where to place and whether the block is supported when they are applied, not when they are admitted. A player's actions therefore give the same world however they are grouped into ticks. The server checks only reach, player overlap and timing at admission; the held item is read from the inventory when the command is applied.

Player inventories are simulation state, changed only by commands in the command phase:

| Command | Effect |
| --- | --- |
| `SetPlayerSlot` | Sets one slot (creative inventory) |
| `PlayerUse` | Uses a block or places the held item; in survival the item is used up |
| `PlayerUseItem` | Uses up a knowledge book outside creative mode (the server gives its recipes); uses the held bucket along the player's view: an empty one takes the first fluid source the view enters before the block it meets, or from that block; a filled one pours into that block or beside it |
| `PlayerBreak` | Breaks a block; in survival it drops what the tool harvests and wears the tool |
| `PickUp` | Moves an item entity, or part of it, into the inventory |
| `DropItem` | Throws one item or the stack from a slot |
| `SwapHands` | Swaps the main hand's stack with the off hand's (the swap key) |
| `EditBook` | Sets the pages of the book and quill in a hotbar slot or the off hand, or signs it into a written book by the player (another stack there is left alone; the server gives the components' encoding) |
| `ContainerClick` | One click in the player's own window or an open container's window |
| `CloseContainer` | Returns the carried stack and the crafting grid to the inventory, or throws them |
| `PlayerDeath` | Drops the whole inventory, the crafting grid and the carried stack around the player; below the world the items are lost |

Every slot change records `player_slot_changed`; a use that opens a container records `container_opened`; taking what a recipe made (from a crafting grid, a stonecutter, a smithing table or a furnace's output) records `recipe_used` with the recipe's kind and index, which the server's recipe book reads. A recipe placed from the book (`PlaceRecipe`, by the same kind and index) without the items for one craft records `recipe_ghost`, and the server shows its ghost. `KnowRecipes` tells the rules the crafting recipes a player knows (learned, forgotten or all of them): with `doLimitedCrafting` on, the crafting grids make only those, once the grid next changes.

Every observable action produces a trace record keyed by (tick, level, phase, root, sequence within the root); a record also names the level of its position. The command phase counts as the overworld's, ahead of every level. Two executions are equivalent only if their trace records are identical, including order. Their canonical state dumps, one part per level, must also be identical.

## Reference rules v10

v10 is v9 with what C2.3 and C2.4 added to the rules: crops that need light, game rules as world state, the day time and the weather. v11 adds C3's entities, TNT and explosions, and v12 C4's components and machines: moving blocks and entities, redstone torches, buttons, plates, targets, daylight detectors, doors, note blocks, honey, every block's push class and conductor, rails and minecarts on them, coral fans, dispensers and droppers. Worlds of an earlier rule set move to the current one with `--migrate-world` ([persistence](PERSISTENCE.md#migrating-between-versions)).

- **Update queue:** neighbor updates and shape updates are queued entries.
  - **Entries:**
    - A neighbor-update entry notifies six neighbors in the order west, east, down, up, north, south, optionally skipping one.
    - A single entry notifies one block.
    - A shape entry updates one neighbor; a change sends shape updates west, east, north, south, down, up.
  - **Order:** an entry emitted while another runs joins the current layer. After each delivery, the layer runs in emission order before the next sibling delivery. An entry emitted outside a chain starts one.
  - **Chain limit:** a chain counts the entries queued in it. Once the count reaches the limit (1,000,000), new entries are dropped and the drop is recorded; entries already queued still run.
  - **Shape nesting:** shape-update nesting is limited to 512.
- **Changes:** a full change runs the removal reactions of the old block and the placement reactions of the new one, then neighbor updates, then shape updates. Quiet changes (state-only changes of repeaters, observers, lamps, comparators, dust, chest pairing and hoppers) skip the neighbor updates. Every state change of a diode updates the block in front of it, and that block's neighbors except the diode itself, before the shape updates.
- **Power:**
  - **Sources:** levers, buttons, pressure plates, target blocks, redstone torches, redstone blocks, repeaters, comparators, observers and dust give power to their neighbors (a torch not to the block it stands or hangs on). A lever, button or plate strongly powers the block it is on, a repeater or comparator the block in front, an observer the block at its back, a torch the block above it.
  - **Conductors:** the blocks both official servers report as redstone conductors in every state (`tests/fixtures/collision/conductor-*.txt`): those whose collision shape is a full cube, except leaves, glass and stained glass, ice, beacons, chorus flowers, copper grates and bulbs, glowstone, sea lanterns, observers, pistons, the redstone block and TNT; soul sand and mud conduct too. Among the blocks with rules of their own: stone, obsidian, lamps, target blocks, note blocks, dispensers and droppers, and slime blocks.
  - **Conductor power:** a conductor that a source powers strongly powers dust and components next to it. Dust powers the block below it and the blocks it points into; a conductor powered only by dust powers components, not dust.
- **Dust:**
  - **Power:** the strongest power its neighbors give it (dust giving nothing), or one less than the strongest dust it reaches on its level, one step up (unless a conductor lies above it) or one step down (unless the block at the side is a conductor). A power change updates the neighbors of the dust and of its six neighbors, in Java hash-set order.
  - **Shape:** stored as the target version stores it: each side none, side or up. Shape updates change it; a dot (no sides) stays a dot while nothing connects; a lone connection extends to the opposite side; a player places a cross. Dust points into the sides its current shape connects, and changes of shape update diagonal dust.
  - **Placement and removal:** dust updates the blocks above and below it and the dust around it, also one step up or down.
  - **Use:** using an isolated cross makes a dot and the other way round.
- **Components:**
  - repeaters: delay 1–4, pulse extension; locked, with the `locked` state, while a powered diode faces into either side;
  - lamps: light at once when an update finds them powered, turn off after 4 ticks;
  - observers: fire 2 ticks after a shape update from the observed side, or after being moved by a piston, with a 2-tick pulse.
- **Support:** dust needs a whole top face or a hopper below it, repeaters and comparators a whole top face, levers, buttons and wall torches a whole face to be on, floor torches and pressure plates the middle of the top of the block below (a sturdy top, or a collision shape that reaches the top there). An update that finds the support gone breaks them with their drops.
- **Plants on their ground** (both official servers; tests/fixtures/collision/plants-*.txt): flowers, saplings, grasses, ferns, bushes, petals, wildflowers and sweet berry bushes grow on soil (dirt, coarse dirt, grass, podzol, mycelium, rooted dirt, moss, pale moss, mud, muddy mangrove roots, farmland); dead bushes and dry grass also on sand and terracotta (1.21.4 not on farmland); fungi, roots and nether sprouts also on nylium and soul soil; wither roses also on netherrack, soul sand and soul soil; azaleas and mangrove propagules also on clay; carrots, potatoes, beetroots, stems and torchflower crops on farmland; nether wart on soul sand; bamboo on soil but farmland, on sand, gravel and bamboo. - **Redstone torches** (both official servers; minecraft.wiki "Redstone Torch"): a torch is turned off by power in the block it is on (a source's, a conductor's strong power, or dust's): an update that finds its state agreeing with that power schedules it after 2 ticks, and the tick turns it off or on. - **Dispensers and droppers** (both official servers; minecraft.wiki "Dispenser", "Dropper"): blocks of nine slots facing any side; comparators read them and hoppers fill and empty them; pistons do not move them. Placing one beside power does nothing until an update reaches it, and power reaching only the block above (from two above, say) waits for one.   - **Ejecting:** an item leaves from 0.7 out of the center toward the front, 0.15625 lower (0.125 facing up or down), as a new item (two draws, replaced), then at a speed of 0.2 plus a draw times 0.1 along the facing and 0.2 up, each axis spread by the difference of two draws times 0.103365, with no pickup delay.

A bucket fills from what a player's bucket fills from; the water bucket takes the slot when it was the last bucket, else the first slot that takes it, else it is ejected; with nothing to fill from, the bucket is ejected. Shears (dispenser_shears) take a full hive's honeycomb in front and wear by one; otherwise they stay. - **Target blocks** (both official servers; minecraft.wiki "Target"): a projectile hitting a target block gives max(1, ⌈15 × (0.5 − e) / 0.5⌉), where e is the larger offset of the hit from the center of the hit face (in double precision), for 20 ticks after an arrow and 8 after a snowball; hits while the target waits are ignored.
- **Scheduled ticks:**
  - **Uniqueness:** at most one pending tick per (position, block). A drained block tick of a block with rules of its own counts as scheduled until it runs; a drained fluid tick does not, so a fluid scheduled again before its drained tick runs ticks twice (lava_flow: receding lava), nor does one of a block without rules of its own (fire, farmland, frosted ice, falling blocks, plants checking their support, big dripleaves, leaves: leaves_decay, leaves updated while their drained tick waits tick again a tick later).
  - **Sub-order:** the level-wide counter is shared by block and fluid ticks.
  - **Priorities:**
    - repeaters: −3 when feeding a diode that does not face back into them, −2 when turning off or ending an extended pulse, −1 otherwise;
    - comparators: −1 when feeding a diode, 0 otherwise;
    - lamps and observers: 0.
- **Pistons:** regular, sticky and slime structures of up to 12 blocks, with quasi-connectivity. Each move takes two ticks.
  - **Extension write order:** a block event writes, in this order:
    1. destroyed blocks, in reverse discovery order;
    2. moving pistons at the destinations, last discovered first;
    3. the head;
    4. vacated cells, in hash order;
    5. the extended base.

    Every write sends shape updates at once. The neighbor updates of the first four follow before the base extends (a note block beside the head plays before it: block_event_order), the base's after it; on a retraction they follow when the action ends.
  - **Retraction write order:**
    1. a still-extending head is cleared;
    2. the base becomes a moving piston;
    3. the head becomes air;
    4. a sticky piston drops its block or pulls.
  - **Push classes:** every block is moved (pushed, and pulled by sticky pistons), destroyed with its drops, pushed only (glazed terracotta: pushed, never pulled; attached to slime it stays behind on a pull) or left in place, as the official servers' pistons treat it; the registry keeps the class of every block (`tools/compile_block_registry.py`: unbreakable blocks are immovable, name rules the rest), checked against both official servers for every block (`tests/fixtures/collision/push-*.txt`) and by pushing and pulling 656 of them (push_classes). A moved block arrives without its water; a moved note block takes the instrument of its new neighbors.
  - **Honey:** honey blocks are sticky like slime blocks, but slime and honey do not hold each other: a sticky block's chain behind it and its neighbors off the axis join only where one of the pair is sticky and they are not slime and honey.
  - **Moving blocks:** moving pistons finish in the block-entity phase two ticks after the event. They block movement and do not conduct power. A sticky piston that retracts before its push finished leaves the block behind.
  - **Destroyed blocks:** dust, levers, buttons, pressure plates, redstone torches, doors, repeaters, comparators, water and wheat in a push line are destroyed. The destruction sends no shape updates; the moving block written there next does (a door's upper half breaks only then). They drop fixed items, placed and launched like every block drop (below), before the block changes. Without data packs fully grown wheat drops wheat and seeds, younger wheat seeds only; with them wheat drops what its loot table rolls (below). Water drops nothing.
  - **Sounds:** after a piston extends, and after it retracts, it draws one number from the level random for its sound's pitch, as both official servers do.
  - **Pushing:** on each of its two steps, before it moves on, a moving block pushes the entities in the space its shape sweeps through in that step (half a block along its motion) out of it, to 0.01 beyond it, by at most the step; all pistons together move an entity at most 0.51 on each axis in one tick. The push moves the entity against the blocks like its own move, and leaves it off the ground unless it pushed it down onto something. A moving slime block also sets the entities' speed along its motion to one block a tick. Moving blocks collide where they stand in their move, so entities rest on them and fall when they move away. A retracting base pushes nothing. Entities that land on a slime block bounce back up at 80% of their speed (items observed). After the push, honey moving sideways carries the entities on the ground whose box meets the space from its top to 1.5 above its cell and whose position lies over it: they move the step with it (also when a sticky piston pulls it).
  - **Heads:** a head removed by anything but its piston (an explosion, a command) takes its extended base, which drops.
- **Hoppers and chests:** push before pull, an 8-tick cooldown, disabled while powered. An item that moves inside a hopper's cell into that space is also taken during its own tick, when the hopper is enabled and not cooling down. Competing hoppers act in block-entity creation order. - **Comparators:** compare and subtract modes with a 2-tick delay; the output signal (0–15) lives in a block entity.
  - **Rear input:** power, also through a conductor, or the fullness of a container behind the comparator; a container behind a conductor replaces a weaker signal.
  - **Side inputs:** dust of any shape, redstone blocks, and the strong power of repeaters, comparators and observers facing in.
  - **Updates:** container changes notify the comparators reading them. A mode change refreshes the output at once.
- **Use:** using a block toggles a lever, presses a button, cycles a repeater's delay, toggles a comparator's mode, or toggles isolated dust between a cross and a dot.
- **Water:** sources, flowing distance 1–7, falling water, 5-tick fluid ticks.

- **Random ticks** (the official 1.21.8 server; random_ticks_farmland, random_ticks_chunks, random_ticks_sections; tests/fixtures/collision/random-ticks-*.txt):
  - **Order:** the chunks whose random ticks run (RandomTickRange) are ticked in the order of an open hash table of their keys (x in the low 32 bits, z in the high): the chunk at 0, 0 first, then the table's slots from the top down, 64 slots while it is at most three quarters full, a key at the slot `mix(key) & 63` (`h = key * 0x9E3779B97F4A7C15`, `h ^= h >>> 32`, `mix = h ^ h >>> 16`) or the next free one. The official servers fill the table as chunks start to tick; Circuit fills it nearest the chunks' center first, which reproduces forced areas.
  - **Per chunk:** randomTickSpeed precipitation checks, each a `nextInt(48)` of the level random that advances the position generator when it is 0 (snow, ice, cauldrons and lightning are not modeled); then, in each section holding a block that takes random ticks or water (waterlogged blocks too; water does nothing in its random tick, but its section is ticked: water_flowing, fitted when water flowed out of the area), from the bottom up, each read as its turn comes (a bamboo stalk grown into the section above makes it ticked in the same chunk tick: bamboo_growth), randomTickSpeed picks: the level's generator `v -> 3v + 1013904223` (mod 2^32) gives x = `v >> 2 & 15`, z = `v >> 10 & 15` and y = `v >> 18 & 15`, and the block there takes its random tick when it is one that takes them. The phase runs serially, after the scheduled ticks; the generator's state is world state (checkpoints keep it).

  - **What they do:** farmland with water up to four blocks away and one above is wetted to 7; otherwise it dries a step, and dry farmland turns to dirt unless a crop or stem keeps it. Crops, stems, grass blocks, mycelium and the plants below act as below. The random ticks of the other blocks change nothing yet.
- **Crops and stems** (the official 1.21.8 server; crops_growth, stems_growth; minecraft.wiki "Tutorial:Crop farming", "Beetroot Seeds", "Melon Seeds"): wheat, carrots, potatoes, beetroots, torchflower crops and melon and pumpkin stems grow only with light 9 or more at their cell (the most of block light and sky light, at any time of day). - **Item entities:** positions and velocities are doubles; each tick, as both official servers do it (checked against their traces):
  - the tick count goes up (it is never reset), and the pickup delay down unless it is 32767 (never);
  - water the item's box reaches (less 0.001 on each side) pushes it, before the move and again after it, by 0.014 along the mean direction of the currents of those cells; each cell's current points toward neighbors holding less water (a cell holds level/9 of a block, a full block under more water) and toward water below an open neighbor, and falling water beside a whole face also flows down; cells reaching less than 0.4 above the item's bottom weigh by that depth, a cell's surface being its height plus its water's, added in single precision (minecraft.wiki "Water"; fitted to the official traces, the precision to item_water_spread);
  - an item more than 0.1 deep loses 1% of its horizontal speed and rises by 0.0005 a tick while slower than 0.06 (single-precision factors); otherwise gravity takes 0.04 from the vertical velocity;
  - an item inside a block (its box, less 1e-7 on each side, overlapping a collision box; minecraft.wiki "Item (entity)", fitted to item_inside_block, item_inside_ways and item_inside_piston) moves out of it: its velocity is scaled by 0.75 and then set, along the way out, to 0.1 plus 0.2 times a float of its own random (seeded with its id, as the reference harness seeds it, after the two floats it drew when it was made), in single precision; the way out leaves the cell holding the middle of its box through the nearest of the cell's north, south, west, east and top faces (ties in that order) whose neighbor is not a full cube (glass and leaves are; slabs, chests, fences, hoppers and soul sand are not), or through the top when none is, never down; it then moves through blocks, keeping whether it was on the ground and not slowed by the block it is in, so that an item at rest pushed straight up still moves only on its fourth ticks;
  - the item moves its 0.25-block box against the collision boxes of every block state (registry data, per version), vertical axis first, then the horizontal axis with the larger movement; an item on the ground with a horizontal speed whose square is at most 1e-5 moves only when its tick count plus its id is a multiple of 4; a move that a collision shortened to a squared length below 1e-7 is not made;
  - collided components stop (a horizontal one only when the collision shortened it by 1e-5 or more); the velocity is damped by 0.98 (horizontally, on the ground, by the slipperiness of the block below times 0.98, in single precision) and an item that lands bounces at half its speed; one that lands on a slime block bounces back at 80% of its downward speed instead, and with less than 0.1 of vertical speed left keeps only 0.4 plus a fifth of that speed of its horizontal speed, as primed TNT and minecarts do too (minecarts twice; slime_landing);
  - when its tick count is a multiple of 40, or even after a move into another block, the item merges with items whose boxes come within half a block of its own sideways (none above or below), in id order: the stacks must be of the same kind and fit in one stack; it takes in a smaller stack and joins an equal or larger one, and the result keeps the younger age and the longer pickup delay. Items of age -32768 or pickup delay 32767 never merge;
  - the age goes up unless it is -32768 (never); at 6000 the item despawns;
  - a cactus whose cell its box reaches (not only the cactus's shape) takes a point of its health at every move, and with none left the item is gone (cactus_damage; other entities are not hurt);
  - (every entity but boats, farmland) a move down off the ground adds to how far it has fallen, made or not (the collided movement), water starts the count again, and a move that lands it gives the fall to the block it stands on: the nearest block whose collision shape meets the bottom of its box, or, with none, the one it met before the horizontal part of the move (the column of that block, 0.2 below its feet, but a fence, wall or gate itself); farmland draws a float from the level random for it;
  - unloaded cells are solid and cells above or below the world empty; an item more than 64 blocks below the world is removed at the start of its next tick (torch_basics), as are arrows, snowballs, minecarts and boats (documented, not compared).
  Items move between chunks with their entities' chunk. They are spawned by commands, by broken and destroyed blocks, by players and on death, and pushed by moving blocks.
- **Experience orbs** (both official servers; orbs, orbs_merge, orbs_more, xp_ores, xp_merge, xp_merge_more; minecraft.wiki "Experience orb", "Experience"): summoned with their value, the orbs merged into them (`Count`) and their age, or given as experience at a point (outside the command phase an orb's first motion waits for its final id, which the commit gives): the experience comes in orbs of the largest of 2477, 1237, 617, 307, 149, 73, 37, 17, 7, 3 and 1 not above what is left, each drawing a slot of 40 from the level random; an orb of that value within half a block whose id is that slot more than a multiple of 40 takes it in (its count grows by one and its age starts again), else a new orb comes, whose first motion is drawn from its own random (seeded with its id, as the reference harness seeds it): a draw for its yaw, then up to 0.2 to each side and up to 0.4 up (1.21.4 draws a double for the yaw and works sideways in single-precision factors). A block a player harvests with a tool gives experience after its drops, at its center: coal ores 0-2, diamond and emerald ores 3-7, lapis ores 2-5, redstone ores 1-5, nether quartz ore 2-5, nether gold ore 0-1 (each one draw of the level random), sculk 1, the sculk catalyst, sensors and shrieker 5, a spawner 15 and two draws of 15; an enchantment that sets it (Silk Touch, by its `minecraft:block_experience` effect in the official data packs) makes it 0 after the draw. Each tick the tick count goes up; with its eye (0.425 above its feet, where it was at the tick's start) in water an orb loses 1% of its horizontal speed and rises by 0.0005 while slower than 0.06, else gravity takes 0.03 from its vertical velocity (on 1.21.8 not inside a block, `OrbMotion`). Inside a block it moves out of it as an item does (its own random has drawn nothing when it was summoned), on 1.21.8 only while its velocity would leave its box inside a block, and it still collides as it moves. It moves its 0.5-block box as items do; its velocity is then damped by 0.98, horizontally on the ground by the slipperiness of the block below times 0.98, in single precision (OrbMotion: on 1.21.4 the vertical drag is in double precision). On the ground it bounces back at 0.4 of the speed it moved with: on 1.21.8 only when that was faster than 0.03, else it keeps what the block left it (nothing, or a slime block's bounce, damped like the rest of its velocity), on 1.21.4 always. When its tick count is 1 more than a multiple of 20 (its first tick among them) it takes in the orbs of its value whose ids are a multiple of 40 apart from its own and whose boxes come within half a block of its own: their counts join its own, and it keeps the younger age. Its age goes up; at 6000 it is gone. Lava its box reaches at the start of its tick takes 4 of its 5 health (fire and explosions hurt it as they hurt items), and lava in its cell makes it jump: 0.2 up and sideways the difference of two floats of its own random times 0.2 on each axis, in single precision. The nearest non-spectator player within 8 blocks (by the positions the server reports, `PlayerPresence`) draws it toward the middle of their body before it moves, by 0.1 times the square of 1 less a eighth of the distance (not compared tick by tick). A player who touches it takes it (`PickUp`): one of its orbs every 2 ticks, gaining its experience, and the last is gone. Experience (gameplay/experience.hpp; the official servers' values after each orb, checked with a protocol client): a player at level L needs 7 + 2L points for the next level below 15, 37 + 5(L − 15) below 30 and 112 + 9(L − 30) from there; points add to the progress their share of that need, in single precision, and each whole level carries the rest over, rescaled to the next level's need; the total counts every point, as a 32-bit sum that wraps and is kept from going below 0. Negative points take progress away and, while it is below 0, levels (at level 0 all experience is gone). The `/xp` command (`ChangeExperience`; client/anvil) sets levels (the progress and total stay), adds levels (below 0 the player has no level, progress or total), adds points, or sets the progress to some points of the level's need (below that need). An anvil takes its cost in levels, an enchanting table an offer's place. Mending, death drops of experience and the experience of mobs, breeding, fishing and trading are not modeled yet.
- **Block drops:** each item a block drops appears within 0.25 blocks of the block's center on each axis, lowered by 0.125, and moves 0.2 up and up to 0.1 to each side, all drawn from the level random (x, y, z, then the two horizontal speeds), as both official servers do. A removed container scatters its contents as both official servers do (exact in their traces): each slot, empty or not, draws a point 0.125 to 0.875 across and 0 to 0.75 up in the cell; its stack leaves in parts of 10 to 30 items, each drawing a block drop's velocity and then a velocity around (0, 0.2, 0) that differs from it by up to about 0.115 on each axis (the difference of two draws times a fitted spread). These parts can be picked up at once.
- **Items:** every item of both versions, 1,415 in all, with its stack size and durability, compiled from PrismarineJS minecraft-data (MIT) at the pinned commit by `tools/compile_item_registry.py`. Items without rules are inert: they can be stored, moved, thrown and picked up. Stacks keep their data components (see [compatibility](COMPATIBILITY.md#content)); stacks merge only when their item, damage and components are equal. A `max_stack_size` component sets the stack's limit, and `max_damage` its durability. Container slots hold up to 99 items, the stack's own limit (usually 64 or less) applying first; a comparator reads a container's fullness against those limits.
- **Other blocks:** every block state of both versions exists, from the block registry `circuit-blocks-1` (compiled from PrismarineJS minecraft-data, MIT, at the pinned commit by `tools/compile_block_registry.py`). Blocks without rules of their own keep all their properties and are inert (sand, gravel and concrete powder fall, and TNT is primed, above): entities collide with their collision boxes, conductors as both official servers report (above), sturdy on faces their collision shape covers (every face when opaque), and water does not flow into them. Pistons treat them by their push class (below). Their hardness, effective tool and harvest tier come from the same data, or, when the server loads data packs, their tool and tier from the block tags (see [data packs](DATA_PACKS.md)). With data packs they drop what their loot tables give (below); a table that does not compile drops nothing. An engine's data is fixed for its life.
- **Player inventories:** each player (profile UUID) has the 46 slots of the player window (crafting result and grid, armor, main inventory, hotbar, off hand), a carried stack and a drag in progress.
  - **Survival use:** placing a block uses one item. A tool wears by one for each block with nonzero hardness it breaks, and breaks at its durability.
  - **Breaking:** a block drops what the tool harvests: stone drops cobblestone, and stone, obsidian, redstone blocks, observers and hoppers need a pickaxe of the required tier (obsidian a diamond one). Breaking a container drops its contents; breaking a piston head removes its base too.
  - **Loot tables:** a block without rules of its own drops from its loot table (`gameplay/loot.hpp`), when the tool harvests it. Pools roll once; entries are items, alternatives, groups, sequences or empty; conditions test survival of an explosion (always, for a player's break), block state properties, the tool's item and enchantment levels, and their combinations; functions set and limit counts. A roll with more than one candidate, or a fortune bonus at a level above zero, would need a random number and drops nothing. Stacks above the item's limit split. The drops are placed like every block drop.
  - **Dig time:** per tick, a block gains the tool's speed divided by its hardness and by 30, or by 100 when the tool does not harvest it, five times less off the ground. Pickaxes, axes, shovels and hoes have the speeds wood 2, stone 4, iron 6, diamond 8, netherite 9, gold 12; swords and shears are not modeled tools.
  - **Pickup:** an item entity whose pickup delay has run out joins the inventory: first the selected hotbar slot and the off hand when they hold the same item with room, then the first slot with room, then the first empty slot. Block drops wait 10 ticks, thrown items 40.
- **Container menus:** a chest (27 slots), a double chest (54, the right half first), a hopper (5), a furnace, smoker or blast furnace (3: input, fuel, result), a barrel (27), a shulker box (27), an ender chest (27: the player's ender inventory), a crafter (9; after the inventory its window shows the result its grid would make, which is no slot, and its properties are each slot's disabled flag and whether it is triggered), a crafting table (10: the result, then the 3x3 grid row by row), a stonecutter (2: the input and the result), a smithing table (4: template, base, addition, result), a grindstone (3: two inputs and the result), a loom (4: banner, dye, pattern item, result; its property is the chosen pattern), an anvil (3: two inputs and the result; its property is the result's level cost), a lectern (1: its book; its property is the page; no inventory slots), an enchanting table (2: the item and the lapis; its ten properties are the three offers' level costs, the low 16 bits of the player's enchantment seed, and the enchantment each offer shows and its level) or a brewing stand (5: three bottles, the ingredient, the fuel; its properties are the brew time and the fuel), followed by the main inventory and the hotbar; or the player's own window. A crafting table's result and grid, a stonecutter's input, result and chosen recipe, a smithing table's or grindstone's slots, a loom's slots and chosen pattern, an anvil's slots, typed name and cost, and an enchanting table's slots and offers belong to the player while the window is open (they are saved with the player's inventory). A furnace's window shows its fuel's remaining and total burn time and its cooking progress and total time as the window's four properties, sent when they change.
  - **Click modes:** pick up and place (left: the stack, right: half or one), quick move (shift), swap with a hotbar slot or the off hand, clone (creative only), throw (one or the stack), drag (split evenly, one each, or full stacks in creative) and collect (double click), with the target version's slot order for quick moves.
  - **Slot rules:** armor slots take only matching armor, one item each. Nothing can be placed in the crafting result or a furnace's result. A furnace's fuel slot takes fuels and a single empty bucket. A brewing stand's bottle slots take one potion, splash potion, lingering potion or glass bottle each, its ingredient slot ingredients and its fuel slot blaze powder (the item tag brewing_fuel); a stack of more than one does not swap with a bottle.
  - **Brewing stand quick moves:** the stand's slots go into the inventory from the hotbar's end; from the inventory fuel goes into the fuel slot (else, as an ingredient, into the ingredient slot), an ingredient into the ingredient slot and a bottle into the first empty bottle slot, or nowhere when that slot does not take it; the rest between the main inventory and the hotbar.
  - **Crafting table quick moves:** the grid goes into the inventory from its start; from the inventory an item goes into the grid (onto stacks of its kind, then the first empty slot), else between the main inventory and the hotbar. The result is shift-clicked as in the own window, from the end of the hotbar.
  - **Stonecutters:** the window's button (`ContainerButton`) chooses one of the recipes that cut the input, by its place in their list (the data packs' stonecutting recipes ordered by id path, then namespace, as both official servers number them); another number does nothing. The result is the chosen recipe's while input is left; taking it (as from a crafting result: onto the cursor, by number key, thrown, or shift-clicked into the inventory from the end of the hotbar until the input runs out) uses one input. Another item in the input, or none, clears the choice. Quick moves send an item some recipe cuts into the input, the input into the inventory from its start, the rest between the main inventory and the hotbar.
  - **Smithing tables:** the template, base and addition slots take the items some smithing recipe takes there (the property sets clients receive). The result is what the first recipe (in id order) that takes the three makes: a transform's result with the base's damage and components, or the base with a trim of the addition's material (each material's `ingredient` before 1.21.5; on 1.21.5 and later the vanilla materials' items, as the items' own `provides_trim_material` component is no data pack's) in the recipe's pattern (before 1.21.5 the template item's, by the patterns' `template_item`); nothing when the base already has that trim. Taking it uses one of each input. Quick moves send an inventory item into the first of the three slots that takes it while empty or holding its kind with room, else between the main inventory and the hotbar; the inputs go into the inventory from its start.
  - **Grindstones:** the inputs take items that wear or hold enchantments. One input with enchantments makes itself with all but its curses (from the data packs' enchantment tag `curse`; an enchanted book left with none becomes a book, which on 1.21.4 keeps an empty stored_enchantments component); two inputs of one item that wears make one with both durabilities and 5% of the most, and the curses of both; the result's repair cost counts the curses kept (doubled and one more for each); nothing else makes anything. Taking the result uses both inputs up and gives experience at the grindstone's center: of the minimum costs of the inputs' enchantments that are no curses, half (rounded up) and a level-random draw below that. Quick moves send an item the inputs take into the upper input, else the lower, while empty, else between the main inventory and the hotbar.
  - **Looms:** the slots take banners, dyes and banner pattern items. The patterns on offer are none without a banner and a dye, else the pattern item's own (the banner pattern tag `pattern_item/<item>`) or, without one, those of the tag `no_item_required`, in the tags' order (`DataPacks::ordered_tag`); a button chooses one of them by its place, another does nothing. When the slots change, a single pattern on offer is chosen, and a chosen one stays chosen where it is still on offer. The result is the banner with a layer of the chosen pattern in the dye's color on top (the server adds layers beyond six; only the client's screen stops at six). Taking it uses a banner and a dye. Quick moves send each item to its slot, or nowhere when that slot holds another; other items go between the main inventory and the hotbar.
  - **Cartography tables** (both official servers, client/maps; with the official data packs, whose item components maps use): the map slot takes filled maps, the slot beside it paper, empty maps and glass panes. A filled map whose data exists makes, with an empty map, two of itself; with paper, while unlocked and below scale 4, one of itself marked to be zoomed (`map_post_processing` 1); with a glass pane, while unlocked, one marked to be locked (0). Taking a marked map makes it a new map, the world's next id: the zoomed one of the next scale over the area around the old center, unexplored; the locked one a locked copy. Each take uses one of each input. Shift-clicks move the result into the inventory from the hotbar's end and the inputs into it from its start; from the inventory a filled map goes into the map slot, paper, empty maps and glass panes beside it, other items between the main inventory and the hotbar.
  - **Anvils** (anvil, chipped and damaged; both official servers, client/anvil; minecraft.wiki "Anvil", "Anvil mechanics"; with the official data packs): placed lying across the player's way (they do not fall yet). The inputs take anything. A repair material of the left item (its material's item tag: `*_tool_materials`, `repairs_*_armor`, phantom membranes for elytra, breeze rods for maces) repairs a quarter of its durability per item, a level each, while it is worn (an unworn one makes nothing). The same item that wears restores both durabilities and 12% of the most, 2 levels when that repairs it; with it, or with an enchanted book, each enchantment of the right input joins the left's: the same level becomes one more, else the higher stays, at most the enchantment's `max_level`; one the left item does not take (its `supported_items`; any goes on a book, and in creative mode on anything) or that an enchantment there excludes (their `exclusive_set`) is left out, a level for each conflict; each joined costs its `anvil_cost` (halved for a book, at least 1) per level, and when every one is left out there is no result. Another right input makes nothing. A typed name (`RenameItem`; the server removes the section sign and control characters, and ignores a name still longer than 50 UTF-16 code units) that differs from the name the item shows (its custom name, its potion's or its item's English name from the official jar's language file) names the result for a level more; a blank one removes a custom name. The name stays for the next items until the window closes. Without any change there is no result; the inputs' repair costs add to the cost; renaming alone costs at most 39 levels; 40 or more is too expensive (no result, the cost shown) outside creative mode. The result's repair cost is the inputs' higher one, doubled and one more unless it was only renamed. The result can be taken only with its cost in levels (any in creative mode), which go: the left input is used up, the right one too, or as many as the repair used. Outside creative mode the anvil wears with a chance of 12% (chipped, damaged, then gone), drawn by a random of Circuit's own from the tick, the player and the place (the official servers draw it from an unseeded random). Quick moves send an inventory item into the first input that is empty or holds its kind with room, else between the main inventory and the hotbar; the inputs go into the inventory from its start. Stacks with several enchantments keep the left's order with the new ones after it (the official servers keep a hash order of their own).
  - **Lecterns** (both official servers; lectern_pages, client/lectern; minecraft.wiki "Lectern"; with the official data packs' item tag `lectern_books` and the books' content components): one modeled type, facing the player who places it, powered or not, holding a book or not; its block entity keeps the book and the page. Used with a writable or written book while it holds none, it takes the book (one of the stack, used up outside creative mode); with a book it opens its window. The window's buttons: 1 the previous page, 2 the next (none past the book's last), 3 takes the book into the inventory (thrown when it has no room), 100 and more a page by its number, within the book; a click on its slot takes the book onto the cursor, a number key into an empty hotbar slot, a throw out of the window. Without its book the window closes. A page turn tells comparators, powers the lectern (every neighbor, the block below strongly; already powered, it stays so) and schedules its block tick 2 ticks later, which ends the pulse; taking the book leaves it without a book and unpowered. Comparators read 1 more than 14 times the page's place in the book (the page over the pages less one, in single precision), 15 for a book of one page, 0 without a book; dust connects to it as to every source. A removed lectern's book pops out first, at its top center a quarter of a block toward its front, launched as every new item is, collectable after 10 ticks; the lectern drops itself.
  - **Enchanting tables** (both official servers, client/enchanting; minecraft.wiki "Enchanting mechanics", "Enchanting table"; with the official data packs; the order of the random draws fitted to 320 windows of the official servers with two other seeds): the item slot takes one of anything, the lapis slot lapis lazuli. While the item can be enchanted (it has an enchantability, from the wiki's table by material: armor 15 leather, 12 chainmail, 9 iron and turtle shells, 25 gold, 10 diamond, 15 netherite; tools and weapons 15 wood, 5 stone, 14 iron, 22 gold, 10 diamond, 15 netherite; maces 15; books, bows, crossbows, fishing rods and tridents 1; and has no enchantments), each change of the slots makes three offers: from the bookshelves around the table (the block tag `enchantment_power_provider`, two blocks away on one axis and up to two on the other, level with the table or one above, with a block of the tag `enchantment_power_transmitter` halfway toward it, each offset halved toward zero; at most 15 count) and the player's enchantment seed, a Java random seeded with the seed draws for each offer in turn 1 to 8 plus half the bookshelves plus up to all of them, of which the first offer costs a third (at least 1), the second two thirds and one more, the third at least twice the bookshelves; an offer below its place (1, 2, 3) is none. Each offer's enchantments are drawn by a random seeded with the seed plus the offer's place: the cost grows by 1 and twice up to a quarter of the enchantability, and varies by a triangular spread of up to 15% (single precision, rounded); of the enchantments of the tag `in_enchanting_table`, in its order, those the item is a primary item for (any for a book), each at its highest level whose `min_cost` and `max_cost` hold the cost, one is picked by `weight`; then, while a draw below 50 is not above the cost, those that conflict with the last are left out and another is picked, the cost halving; a book loses one of them, drawn at random. The offer shows one of them, drawn next. An offer is taken (`ContainerButton` 0-2) with lapis and levels at least its place and levels at least its cost, any in creative mode: the item gets the enchantments (a book becomes an enchanted book with them stored), the player loses its place in levels and lapis, and the seed changes (by a random of Circuit's own; the official servers draw it at random). A player's seed is Circuit's own from the player until enchanting first changes it. Quick moves send the item and the lapis into the inventory from the hotbar's end, lapis into the lapis slot, one of another item into the empty item slot, else nowhere. Stacks with several enchantments keep the order they were drawn in (the official servers keep a hash order of their own).
  - **Furnace quick moves:** the result goes into the inventory from the hotbar's end; the input and fuel into the inventory from its start; from the inventory, an item a recipe of the furnace's kind takes goes to the input, else a fuel to the fuel slot (an empty bucket is no fuel here), else between the main inventory and the hotbar.
  - **Crafting:** with data packs, the result slot shows what the first matching recipe in id order makes from the own window's 2x2 grid or a crafting table's 3x3 grid (`gameplay/recipes.hpp`); recipes are ordered by the id's path, then its namespace, as both official servers order recipes of several namespaces (client/ns_crafting; furnaces take the first of their recipes in the same order, and the recipe book numbers recipes in it, client/ns_book):
    - shaped recipes anywhere in the grid, also mirrored;
    - shapeless ones in any order;
    - transmute recipes, whose result keeps the input's components unless the input already is the result item.
    Taking the result crafts once: onto the cursor (left or right click, when all of it fits), into an empty hotbar slot or the off hand (number keys), thrown (`Q`, or `Ctrl+Q` again while the result stays the same item), or shift-clicked into the inventory from the end of the hotbar until the result changes item or nothing moves (what does not fit is thrown). Each crafting uses one item of every grid slot; buckets of milk, water and lava leave a bucket, honey bottles and dragon's breath a glass bottle, in the slot when it is empty, else in the inventory or thrown. Without data packs there are no recipes.

They make (client/special_a, client/crafter_special, client/fireworks and client/crafter_fireworks, both official servers; `gameplay/recipes.hpp`):
    - repairing: two stacks of one damageable item and nothing else (damaged or not) give one of it with both durabilities left and 5 % of its durability (rounded down) more, at most whole; of their components only the curses stay, each at the higher of its levels (a dyed color goes too);
    - armor dye: one dyeable item (the item tag dyeable) and one or more dyes give the item with its color, if any, and the dyes' mixed (minecraft.wiki "Dye": the averages of red, green and blue scaled by the average largest channel over the largest average, in integers);
    - banner copying: a banner with patterns and a blank one of the same color, nothing else, give a copy; the patterned banner stays in its slot (in a crafter it is thrown out after the copy);
    - shield decoration: a shield without patterns and a banner give the shield with the banner's patterns and color (a base color of its own replaced); a shield with patterns is refused;
    - firework stars: one gunpowder, one or more dyes and at most one each of a shape item (a fire charge: a large ball; a gold nugget: a star; a mob head: a creeper; a feather: a burst; none: a small ball), a diamond (a trail) and glowstone dust (a twinkle), nothing else, give a star with the dyes' firework colors in grid order (minecraft.wiki "Firework Star");
    - firework rockets: one paper, one to three gunpowder and any stars, nothing else, give three rockets that fly as long as the gunpowder and hold the stars' explosions in grid order (a star without one adds none); with one gunpowder and no explosions the rockets have no components (the item's default);
    - star fades: one star and one or more dyes, nothing else, give the star with the dyes as its fade colors in grid order, replacing earlier ones (a star without an explosion becomes a small ball without colors).
    The special recipes are not limited by `doLimitedCrafting`, and taking what they make records no recipe for the recipe book.
    A grid slot emptied by a pickup or a throw, and one that keeps a remainder when the result is taken, records two changes; the server sends the result again for each change a click makes (client/own_grid_counts).
  - **Closing:** the carried stack, the crafting grids, a stonecutter's input and a smithing table's, grindstone's, loom's, anvil's or cartography table's inputs and an enchanting table's item and lapis go back to the inventory (hotbar first), or are thrown when it is full; the results empty, the stonecutter's choice clears, an anvil's typed name is forgotten and an enchanting table's offers end. A crafting table's window also closes this way when the table goes. When the player leaves, the grids and the carried stack are thrown instead (`CloseContainer` with `drop`), as the official servers drop a departed player's menus.
- **Maps** (both official servers, client/maps; minecraft.wiki "Map"; with the official data packs): an empty map a player uses becomes a filled map of a new map, the world's next id (from 0), of scale 0 over the 128-block area of the grid (corners at -64 plus multiples of 128) that holds the player's feet, in the player's level. In survival the last empty map in the hand becomes the filled map; else one is used up and the filled map goes into the inventory, dropped without room; creative players keep the empty map. A map keeps its center, scale (0 to 4: 128 << scale blocks across, its areas aligned to that grid), dimension, lock and colors. Players carrying a filled map get its data: the whole map the first time, then each tick its markers when they changed and the rectangle of pixels that changed. A carrier within 63 pixels of its center (pixels of 1 << scale blocks) shows as a player marker at twice its offset plus 0.5, truncated, facing its wrapped yaw 8 degrees further from 0 in whole sixteenths; one beyond that but within 320 pixels on both axes shows on the edge, facing nowhere; one farther, not at all.
- **Maps exploring** (both official servers identical, client/maps_explore and probes over built terrain, every pixel matched by the model below; minecraft.wiki "Map" and "Map item format"): once every level ran, each player explores the unlocked filled maps of their level in their main hand, then their off hand.
  - **When:** each (map, player) counts a step on each tick the map explores; a player who no longer carries the map is forgotten, and holding it again counts from 1. An explore scans the map's columns (pixels along x, within the radius of the player's pixel) whose x is the step modulo 16, and the column after each scanned column in which a pixel changed, so a new map fills at once from its first scanned column on and the columns before it come when the step reaches them.
  - **Where:** the radius r is 128 blocks in pixels (128 >> scale); a pixel is drawn when its squared distance d² from the player's pixel (the floor of the player's position) is below r², the pixels in the outer two (d² above (r − 2)²) only when x + z is odd.
  - **Colors:** a pixel covers n by n columns (n = 1 << scale). In each column the highest block whose color is not NONE gives its color and height; water, and blocks holding water that do not bear a block on their whole top (barriers always, never rails, ladders, iron bars, chains or glass panes), give WATER and the depth of the blocks holding water from there down. A column without blocks is stone (the End's void). The pixel takes the most common color of its columns, ties going to the one met first (x by x, z by z within). The colors of block states come from the official servers: every state the probes placed (tests/fixtures/maps/colors-*.txt; by a log's axis, a bed's part, wheat's age; pale oak leaves, closed eyeblossoms and pale oak saplings differ by version), compiled by tools/compile_map_colors.py.
  - **Shades:** water by the depth summed over the columns divided by n² (rounded down): bright when it plus twice the parity (x + z odd) is below 5, dark from 10 on even pixels and from 7 on odd ones; other colors by the heights summed over the columns against the pixel north of it (outside the map too): bright when 20 times the rise is at least (4 − 2 parity) n² (n + 4), dark when it is at most −(2 + 2 parity) n² (n + 4), else normal. At scale 0 that is higher, level or lower than the block north.
  - Maps in levels with a ceiling (the Nether) do not explore: the official servers draw a pattern there that is not described publicly. Maps read only loaded columns (the official servers load the columns they read; with the default view distance of 6, Circuit's players keep the chunks within 8 of theirs loaded, which a map's 128 blocks stay within). Item frames are not modeled.
- **Death drops:** in the target version's order (hotbar, main inventory, armor from the feet up, off hand), then the crafting grids (the own window's, then an open crafting table's), an open stonecutter's input, an open smithing table's, grindstone's, loom's, anvil's and cartography table's inputs, an open enchanting table's item and lapis and the carried stack, each with a 40-tick pickup delay. They spread in eight directions at 0.25 and then 0.125 blocks per tick, and 0.2 upwards; the target version picks each direction and speed at random.
- **Chunk tickets and levels** (minecraft.wiki "Chunk", observed on both official servers):
  - **Tickets:** a ticket has a type, a level, a square radius and an optional lifetime in ticks. The chunks of its square take its level; every chunk further out takes one level more per chunk of Chebyshev distance. A chunk takes the lowest level of any ticket.
  - **Load level:** from every ticket but a player's simulation ticket. 31 and lower is entity ticking, 32 block ticking, 33 border; higher is not loaded.
  - **Simulation level:** from every ticket but a player's loading ticket, and never lower than the load level. At 32 and lower scheduled ticks, block events and block entities run; at 31 and lower entities too.
  - **Random ticks:** 1.21.8 runs them where the simulation level is 31 or lower. 1.21.4 runs them where it is 32 or lower and a non-spectator player stands less than 128 blocks horizontally from the chunk's center.
  - **Idle levels:** a level with neither players nor forced chunks stops its entities and block entities 300 ticks after it last had them, or after the server started. They resume as soon as it has them again.
  - **Server tickets:** the start ticket at the spawn chunk (level 32 − spawnChunkRadius, 2 by default); per player, a loading ticket over their view distance (level 31) and a simulation ticket at their chunk (level 31 − simulation distance). Only forced and portal tickets survive a restart.
  - **Changes** apply in the level's chunk stage, after its scheduled ticks, as on the official servers: a chunk that a command drops still runs that tick's scheduled ticks. Lifetimes end at the chunk stage they reach.
  - **Unload and reload** (both official servers): unloading keeps all chunk state. A dropped chunk's pending ticks keep the delay they had left, counted from the tick after it dropped; after a reload they wait out that delay, and the chunk's scheduled ticks and block entities run again two ticks after the reload, its pending block events at once. A reload increments the chunk generation, and commands can name the generation they expect.
  - **Entities with their chunk:** the entities of a chunk that unloads leave the level (removed as unloaded) and are kept with it; after a reload they come back in the chunk stage of the next tick, column by column in coordinate order and by their old ids, under new ids from the shared counter and with their tick counts starting again, and they tick again two ticks after the reload. The official servers load them back in the order of their chunk maps, which varies; a reloaded entity's new id changes when it moves at rest (item_chunk_edge passes; three entities in three chunks came back in different orders on the two versions).
- **Light** (minecraft.wiki "Light"; both official servers, compared with light probes):
  - **Per state:** an emission (0–15), a dampening (0, 1 or 15) and, for slabs, stairs, snow, farmland, dirt paths, pistons and a few others, an occlusion shape. The block registry holds them for every state of both versions, from minecraft-data with Circuit's own state rules (lit blocks, candles, sea pickles, waterlogged states and so on); a report of every state from both official servers matches it exactly.
  - **Spreading:** light passes to a neighbor one level lower, or lower by the neighbor's dampening when that is more, unless the faces of the two cells' occlusion shapes between them together cover the face. Block light starts at emitters; sky light starts above the world, and level 15 passes straight down undiminished into cells that dampen nothing.
  - **Timing:** light follows the blocks as they were at the end of the previous tick: a change made in one tick shows in the next. The engine keeps those blocks and brings the light up to date when it is read, following changes incrementally (columns that load and unload, cells that change); the result does not depend on when it is read.
  - **Rules that read it:** a rule reads the most of a cell's block and sky light as of the start of the tick, in any phase: the command, random-tick and block-entity phases bring the light up to date before they run when they may read it; another phase brings it up to date the first time one of its roots reads it (serially; the light depends only on the blocks at the start of the tick, so it does not matter which root asks). Wheat grows only with light 9 or more at its own cell (minecraft.wiki "Wheat Crops"). Daylight detectors read the sky light, in the block-entity phase and when used by a command. Mushrooms read the light when an update checks them (mushrooms: a roof removed, glowstone set or a piston pushing beside them; an update in the tick a light source arrives still sees the light before it).
- **Game rules** (minecraft.wiki "Game rule"; both official servers):
  - **World state:** a `SetGameRule` command sets one of the version's rules, but not an experimental one. A boolean rule takes 0 or 1, spawnChunkRadius 0–32, and every other integer rule any value, as on the official servers; other values are refused. The state holds the rules away from their defaults; it is saved in checkpoints, and the commands are logged.
  - **Read by the rules:** randomTickSpeed is the number of random positions each section of a random-ticking chunk gets per tick; none at 0 or below. tntExplodes primes TNT (below), doDaylightCycle and doWeatherCycle advance the day and the weather, waterSourceConversion and lavaSourceConversion make sources, and doFireTick and allowFireTicksAwayFromPlayer let fire act (below). The server reads spawnChunkRadius for the spawn chunks and sets rules with `/gamerule` ([server guide](SERVER.md#survival-and-inventories)). The other rules are kept but change nothing yet.
- **Difficulty:** the world has one difficulty, peaceful (0) to hard (3); a new world is peaceful. A `SetDifficulty` command sets it; the server sets its configured difficulty at every start. It is saved in checkpoints and Anvil worlds. Fire spreads more readily the harder it is; nothing else reads it yet.
- **Day time** (minecraft.wiki "Daylight cycle"; both official servers): the world has one day time, in ticks (24,000 a day), as only the overworld has a daylight cycle. A new world starts at 0. A `SetDayTime` command sets it (never negative); after the commands of each tick it advances by one while doDaylightCycle is on, so a change in a tick shows one more at its end. It is saved in checkpoints.
- **The sky** (minecraft.wiki "Daylight cycle", "Light"; checked with daylight detectors on both official servers): the time of day runs from 0 at noon to 1 over a day, slower around noon and midnight: with d the fraction of the day since day time 6,000, (2d + (1 − cos πd) / 2) / 3 in single precision; the sun's angle is that fraction of a full turn. Before the day time advances in a tick, the sky's darkening (0 to 11) is computed from the weather after it advanced and the day time: with c the cosine of the sun's angle held to −0.25..0.25, ⌊11 × (1 − (0.5 + 2c) × (1 − 5r / 16) × (1 − 5tr / 16))⌋ for rain level r and thunder level t. The cosines come from a table of 65,536 single-precision sines, as on the official servers. The darkening holds until the next tick computes it again; a restored world derives it. Nothing in the rules reads it yet.
- **Weather** (minecraft.wiki "Weather" and "Commands/weather"; both official servers, compared with a protocol client and their saved level data): one weather for the world, the overworld's.
  - **Flags and timers:** a rain flag and a thunder flag, each with a timer, and a clear timer. While the clear timer runs, both flags are off and their timers wait at 1; when it ends, both flags turn on, so a clear spell ends in a thunderstorm. Otherwise a timer counts down and toggles its flag when it reaches 0; a timer at 0 draws its flag's next duration: rain on 12,000–24,000 ticks, off 12,000–180,000; thunder on 3,600–15,600, off 12,000–180,000. Timers run only while doWeatherCycle is on.
  - **Commands:** a `SetWeather` command is `/weather`: clear for a duration sets the clear timer and turns both flags off with their timers at 0; rain or thunder sets both timers to the duration and turns rain on, and thunder only for thunder. A duration of 0 draws the kind's default (clear 12,000–180,000, rain 12,000–24,000, thunder 3,600–15,600).
  - **Levels:** after the timers, the rain and thunder levels move toward their flags by 0.01 a tick in single precision, within 0 and 1, whatever the game rule. Rain shows while the rain level is above 0.2. A start (`LevelsStarted`) sets the levels to their flags, as when the official servers load a world.
  - **Order:** in each tick, after the commands, the weather, then the day time.
  - **Randomness:** the official servers draw durations from the level's random sequence; Circuit draws them from its own stream for each tick, so durations differ while their ranges are the same. Everything else matched the official servers exactly, level values included. Lightning, snow and ice, filling cauldrons and other effects of rain are not modeled.

## Part I mechanism contracts

Every supported mechanism runs in the region-parallel runtime under the same rule.

- **Execution:** a root may touch only the columns its region owns.
- **Conflict fallback:** touching another region's column aborts the attempt. The affected regions roll back, merge, and run again in serial order. Repeated conflicts end in one region, which is serial execution through the same machinery.
- **Level-wide order:** level-wide counters are staged and assigned at commit in serial order.

## Region-parallel runtime

**Ownership.** Every loaded chunk column belongs to exactly one region. A region's columns are all of one level. A region task runs its roots in the phase's serial order and may touch only its own columns. A read or write of a column owned by another region throws before touching it.

**Conflicts.** The coordinator rolls back an aborted attempt using copy-on-first-write snapshots of the written columns. It then merges the two regions, discards any staged results of the merged regions, and runs the merged region again. Regions that never touched each other keep their results. Each conflict reduces the number of regions, so a phase always finishes; in the worst case everything becomes one region and runs serially.

**Level-wide counters.** These are not drawn from shared counters during a phase:
- scheduled-tick sub-orders;
- block-event queue positions;
- the creation order of block entities created during a phase (moving pistons);
- the ids of entities spawned during a phase (drops).

Each region context keeps a creation ledger per counter. Every creation adds a (root, sequence) entry, and the staged object points at its entry.

- **Commit:** the coordinator sorts the entries of all regions and assigns counter values in serial order. Then it applies the values to the objects that still exist.
- **Removed objects:** creations whose objects were removed again within the phase still consume their values, as they do in the serial order. A moving piston's head that is created and removed in the same block-event phase is one example.
- **Rollback:** an aborted attempt discards its ledger along with its writes.

Entities spawned in parallel roots hold provisional ids until commit. Commit rewrites them in storage, the entity index and the trace, including the ids of entities that were removed again.

**Block-event order.** Each region drains its own FIFO. At commit, the global FIFO order is rebuilt from the initial queue and the children each event appended. Trace records are renumbered to their global positions.

**Why layout cannot change results.** Within a phase, regions that finished without conflict accessed disjoint columns. Their roots therefore commute with each other's roots and see exactly the column states they would see in the serial order. Region layout decides only what runs concurrently.

**Layouts.** `adaptive` merges on conflict and, every 20 ticks, splits regions whose columns have not interacted for 40 ticks. `single_region` runs everything through one region. `perturbed` applies seeded random merges and splits for testing.

**Threads.** `PoolRunner` runs each region task as one job on the Asio pool; workers never wait for other jobs. `SeededRunner` interleaves task steps deterministically on one thread from a seed, optionally injecting aborts, so any failure replays exactly.

## Verification

- `rules_tests` checks hand-derived expectations for every mechanism, including:
  - chunk-edge crossings, and a chain returning across an edge within one tick;
  - pulse extension, priority order and diode priorities;
  - chain truncation;
  - piston limits, and observers watching and being moved by pistons;
  - conservation in hopper races, water timing and stream locality;
  - generation checks, command validation and capacity failure;
  - ticket and spawn bounds at their endpoints and at extreme or aliasing coordinates.
- `simulation_tests` compares fourteen scenarios with the oracle, trace by trace every tick and state by state at checkpoints.
  - **Configurations:** 1/2/4/8/16 pool workers, a single region, seeded random and priority interleavings, injected aborts, and perturbed layouts.
  - **Transient objects:** the `transient_heads` scenario and a hand-derived case check that block entities created and removed within one phase still consume their creation order.
  - **Bounded exploration:** 64 seeds of random placements of redstone components, pistons, slime, hoppers, chests and stone around a chunk corner, for 60 ticks each, under seeded interleavings and perturbed layouts. Every tick is compared with the oracle.
  - **Input rejection:** out-of-range spawns and tickets are rejected on both executors without effect.
  - **Negative check:** a deliberately unsafe mode without ownership checks must produce a detected divergence.
- `control_tests` checks seeded-schedule reproducibility, tick-clock catch-up and the state digest.
- `evidence_tests` covers:
  - the [trace fixture format](TRACE_FORMAT.md) and the content mapping;
  - recording and evaluation on both the engine and the oracle;
  - the committed reference recordings;
  - every target-version trace in `tests/fixtures/harness/`, on a 4-worker engine and on the oracle.
- `contract_tests` checks the compatibility table:
  - every row claims a tier;
  - L0 claims need target-version traces and list no gap;
  - L2 claims list their gaps.

GCC AddressSanitizer, UndefinedBehaviorSanitizer and ThreadSanitizer runs of the test programs are part of milestone checks. The `ubsan` mode stops at the first diagnostic. ThreadSanitizer needs ASLR disabled for the test process (`setarch "$(uname -m)" -R`). See the [development guide](DEVELOPMENT.md).

## Workload profile

The profile measures five generated workloads (`tests/fixtures/workloads/`, from `tools/generate_workloads.py`) for 600 ticks after their setup settles. The target version was measured by the external harness, and Circuit by `--profile-fixture` on a release build.

- **Machine:** Intel Core Ultra 7 270K Plus, 24 logical CPUs, Linux 6.18 under WSL2.
- **Target version:** OpenJDK 21.0.12.
- **Circuit:** GCC 13.3.

| Workload | Target version: mean tick, largest phases | Circuit, 1 worker | Circuit, 8 workers |
| --- | --- | --- | --- |
| 256 observer clocks | 0.48 ms: block ticks 74%, random ticks 22% | 0.54 ms | 0.69 ms |
| 64 dust clocks | 3.97 ms: block ticks 97% | 2.49 ms | 2.61 ms |
| hopper lines | 0.27 ms: block entities 57%, random ticks 37% | 0.24 ms | 0.30 ms |
| piston engines | 0.75 ms: block events 43%, block ticks 25%, block entities 16%, random ticks 16% | 0.61 ms | 0.75 ms |
| water flood | 0.23 ms: fluid ticks 56%, random ticks 36% | 0.12 ms | 0.19 ms |

In these workloads the ordered phases dominate the target version's tick: block ticks, fluid ticks, block events and block entities. Their roots belong to independent machines. The claimed tiers therefore do not force serial execution: regions that do not interact may run concurrently, because commit restores the level-wide order.

Circuit does not yet gain from this. With 8 workers it is 5–55% slower than with one, because coordination, snapshots and serial commit cost more than the parallel work saves on ticks of this size.

These numbers are not a performance claim:
- the semantics differ (L2 rows, no lighting, no networking or chunk sending);
- only means were recorded;
- tail latency is not measured.

Optimization belongs to M8.

## Running

```bash
xmake run circuit-server --simulate --ticks 300 --workers 4 --record "$PWD/demo.crpl"
xmake run circuit-server --simulate --replay "$PWD/demo.crpl" --workers 16
xmake run circuit-server --simulate --ticks 200 --realtime
xmake run circuit-server --compatibility
xmake run circuit-server --profile-fixture "$PWD/tests/fixtures/workloads/observer_clocks.ctrace" --workers 8
```

`--simulate` without `--replay` runs a built-in demonstration with machines that straddle chunk edges.

- **Replay records:** records (format version 20) store the bundle, the rule-set id and the block registry id, whose encoding their block states use. Each command names its level. Item stacks carry their data components, which the simulator checks against the bundle's protocol. A record made under different reference rules or another block registry is refused with `rules_mismatch` instead of replaying with silently different behavior. Older records are still read:
  - version 19: the same commands, without slot toggles;
  - version 18: also without window buttons;
  - version 17: also without closed windows whose items drop;
  - version 16: also without the difficulty;
  - version 15: also without uses of items along the player's view;
  - version 14: also with player uses that do not give the player's yaw (read from their horizontal facing);
  - version 13: also with player uses that do not say where they clicked (read as the middle of the block);
  - version 12: also without summoned entities;
  - version 11: also without the pickup delay and age of spawned items;
  - version 10: also with positions and velocities in 1/4096-block units, read exactly as doubles;
  - version 9: also without weather;
  - version 8: also without day times;
  - version 7: also without game rules;
  - version 6: tickets are read as forced ones of level 31 over their radius;
  - version 5: also, every command is the overworld's;
  - version 4: also, stacks have no components;
  - version 3: also, the record predates the registry and is read as `circuit-blocks-1`.
- **Digest:** the output includes a 64-bit state digest. Equal digests across worker counts are a quick check, not proof.
- **`--realtime`:** paces ticks at 20 Hz. When it falls more than 40 ticks behind, it drops the wall-clock backlog; logical ticks are never skipped.

Fixtures in [circuit-trace format](TRACE_FORMAT.md) can be checked with `--check-fixture <file>`, or recorded with `--record-fixture <skeleton> --output <file>`.

## Limitations

- Rows claimed L2 differ from the target version as listed in the compatibility table. The main gaps are:
  - simplified item pushing by moving blocks;
  - items are not moved by lava, bubble columns or waterlogged blocks; entities come back with their chunks in coordinate order, not in the order of the official chunk maps; recovery after a restart continues the simulation exactly, so entities keep their ids and tick counts, where an official server loads them with new ones; entity UUIDs are not world state (the server derives them from entity ids; C11);
  - random ticks of blocks other than farmland, crops, stems, grass, mycelium and the growing plants changing nothing, and the chunk order of a load history modeled for forced areas only;
  - chunk tickets: no teleport, portal or ender pearl tickets yet; new chunks load at once (the official servers take 2 to 4 ticks, varying between runs); dropped chunks unload at once and reloads happen in the chunk stage (the official servers may keep a dropped chunk at border for a tick or two, and restore a cached chunk during the command, which moves restored ticks by a tick between runs; in the open trace `tnt_reload_pending` a repeater's pending tick runs a tick later than Circuit's);
  - container menus without the special recipes of cloning, map extending, tipped arrows and decorated pots, and a recipe placed from the book at a crafting table showing the first recipe in id order that takes the grid, where both official servers show the placed one's result until the grid changes (client/ns_place); loot tables without their random parts, and fixed drops for the modeled blocks.
- Blocks without rules of their own (but those that fall and TNT, above), among them coral blocks and coral plants, are inert: solid when they have a collision shape, conductors as the official servers report, pushed by pistons without the shape changes their new neighbors would give them (fences, walls, panes, note blocks), and drop only from deterministic loot tables (without data packs, nothing, also when an explosion breaks them). Redstone, explosions and burning arrows prime TNT blocks, and dispensers prime TNT items; fire and flint and steel do not. Dispensers do not shoot, place fire, boats or blocks, use shears, bottles or honeycomb, or equip players. Explosions do not hurt or push players, and entities of one chunk section are hurt in id order rather than the order they entered it. Of the TNT duplication machines, only the Mytteri push duper is established (below); other designs are untested. See [technical machines](COMPATIBILITY.md#technical-machines).
- Light at the edge of the loaded area is not compared with the target versions. There is no world generation or mob spawning, and players cannot reach the Nether or the End.
- Snapshots copy whole column data on first write, and commit is serial. On the measured workloads, coordination overhead outweighs parallel gains.
- Commands validate their inputs before using them; for example, a spawn position must be finite and inside the world border and the world's height, and a velocity at most 64 blocks per tick on each axis (a Circuit capacity). Out-of-range input is rejected with no effect.
- A capacity failure, such as exceeding 1,000,000 block events in one tick, fails the tick and leaves the engine unusable. Nothing is silently dropped. The neighbor-update chain limit is the exception: it drops updates as the target version does, and records it.
